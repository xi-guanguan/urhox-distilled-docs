# 移动平台检测与响应式适配方法论

> **这是什么**：从《节拍前夜》的手机／电脑布局区分实践中，提炼平台识别、布局选择、输入兼容与检测生命周期的设计方法。
>
> **来源**：节拍前夜项目实战，AI 辅助代码研究与整理
> **推荐度**：L2（现有实现经过静态核查；阈值判断存在误判边界，推荐重构方案尚未实现或实机验收）
> **适用场景**：UrhoX / TapTap Maker 游戏的原生移动端、桌面端、Web 预览，以及手机、平板、高 DPI 与触屏电脑适配
> **核查范围**：研究时的项目代码；不代表所有引擎版本或所有宿主环境的行为

---

## 一、核心原则：不要用一个“是否手机”包办所有决策

必须分清三个问题：

| 维度 | 回答的问题 | 典型用途 |
|------|------------|----------|
| 平台身份 | 当前运行在什么系统或宿主上？ | 原生平台能力、宿主差异 |
| 布局模式 | 当前画面适合哪一种布局？ | 按钮排列、字号、紧凑布局、双手操作区 |
| 输入能力与状态 | 能使用哪些输入？最近实际用了什么？ | 触摸、鼠标、键盘兼容与操作提示 |

**触摸不等于手机，小窗口不等于手机，高 DPR 也不等于手机。**

原生平板属于移动平台，但可以使用宽屏布局；触屏电脑支持触摸，不必因此被当成手机；手机连接键盘后，仍应允许键盘操作。

## 二、现有实现：平台优先，模拟其次，屏幕特征兜底

统一入口是 `Settings.IsMobilePlatform()`，按照以下顺序执行，命中后立即返回：

| 优先级 | 条件 | 现有结果 |
|--------|------|----------|
| 1 | 平台工具识别为 Android、iOS 或 HarmonyOS | 移动端布局 |
| 2 | `input.touchEmulation` 为 true | 移动端布局 |
| 3 | `DPR >= 2.0` 且逻辑短边 `<= 500` | 移动端布局 |
| 4 | 以上条件都不满足 | 非移动端布局，即项目中的电脑布局 |

逻辑短边的计算：

```lua
local dpr = graphics:GetDPR()
local logicalShort = math.min(graphics:GetWidth(), graphics:GetHeight()) / dpr
```

示例：物理画面 `2400 × 1080`、`DPR = 3`，逻辑短边为 `360`，满足兜底条件。

这里读取的是当前渲染画面的宽高，不应把它无条件当成整块硬件屏幕的分辨率。

旧接口 `Settings.IsSmallScreen()` 已直接委托给 `Settings.IsMobilePlatform()`。虽然名字仍叫“小屏幕”，实际语义已经变为“是否采用移动端模式”。新代码应避免继续传播这个命名歧义。

### 为什么不再用物理像素阈值

旧版以物理长边 `>= 1280` 作为电脑判断依据，现代手机横屏通常也有 2000 以上的物理像素，导致手机布局分支被跳过。

**物理像素适合描述渲染尺寸，不适合直接推断设备类别。**

## 三、这个判断当前影响什么

| 项目行为 | 移动端 | 电脑端 |
|----------|--------|--------|
| 默认 UI 个性化倍率 | 1.2 | 1.0 |
| 技能按钮基础尺寸 | 100 | 80 |
| 跟拍按钮基础尺寸 | 210 | 170 |
| 战斗操作区 | 默认左跟拍、右技能，可交换左右手 | 居中横排 |
| 操作设置 | 换手与按钮缩放 | 键位绑定 |
| 弹窗 | `fullscreen` 降级为 `xl` | 保持请求尺寸 |
| 安全边距 | 按设计尺寸的 4% 估算 | 0 |

这些都是项目策略，不是引擎通用默认值：

- 玩家已保存的 UI 倍率优先于默认倍率。
- 按钮基础尺寸处于项目 UI 设计空间，不是屏幕上的最终物理像素尺寸。
- 4% 边距只是项目估算，不是设备真实安全区域，也不能保证避开所有刘海或宿主覆盖层。
- 当前战斗仍持续处理键盘输入，并未因移动端布局而禁用键盘。

## 四、现有实现的三个风险

### 1. 屏幕兜底没有限制为 Web

实现注释称 DPR 与逻辑短边判断用于 Web 手机预览，但实际没有检查 `IsWebPlatform()`。

结果：高 DPI 桌面小窗口也可能满足条件，被误判为移动端。

即使加上 Web 限制，桌面浏览器的小窗口仍可能满足相同条件。所以这只能作为低置信度启发式，不能升级为准确的硬件身份识别。

### 2. 首次判断后永久缓存

现有 `Settings` 会缓存首次结果，无论结果为 true 还是 false，后续都不重新检测。

而且战斗 UI 模块在 `require` 阶段就读取移动端标志与安全边距，早于 `Start()` 中的 UI 初始化，并另存为模块局部值。

如果预览配置、DPR 或画面尺寸随后改变，就可能沿用旧判断。即使普通界面重建，Lua 模块顶层也不会因此再次执行。

**重置中央检测缓存还不够，消费方保存的布局快照也必须同步刷新。**

### 3. 个别组件绕开统一入口

延迟校准按钮另用 `Android/iOS 或 input.screenKeyboardSupport` 判断。

软键盘能力并不等于手机身份；这套规则也没有覆盖统一入口中的触摸模拟与 DPR 兜底，HarmonyOS 未显式包含。

结果：同一画面不同组件可能采用不同的手机／电脑尺寸策略。

## 五、推荐设计：统一快照，但分开决策

以下是推荐方案，**不是已经完成的项目改动**。

### 1. 统一收集环境信息

由一个模块提供可解释的环境快照，例如：

- `platform`：平台或宿主名称。
- `nativeMobile`：明确的原生移动平台身份。
- `touchEmulation`：是否启用触摸模拟。
- `physicalWidth`、`physicalHeight`、`dpr`、`logicalShort`。
- `layoutMode`：最终布局模式。
- `reason`：命中原因，如 `native-platform`、`touch-emulation`、`web-size-heuristic`、`user-override`。

输入能力只有在宿主提供可靠接口或实际输入事件时才记录；不要用 `touchEmulation == false` 推断“不支持真实触摸”，也不要把当前没有手指按下推断为“电脑”。

### 2. 为布局提供明确的覆盖选项

建议允许用户或开发调试选择：

- 自动。
- 移动端布局。
- 电脑端布局。

在自动模式下，原生平台身份与预览明确配置优先；Web 屏幕特征只做可覆盖的兜底。独立的响应式断点继续根据可用空间决定横排、纵排或紧凑布局。

手动覆盖只改变布局，不伪造平台身份，也不禁用其他输入设备。

### 3. 管理检测与布局刷新生命周期

1. 模块加载阶段不读取并固化可变的屏幕参数。
2. 在宿主配置与 UI 初始化就绪后取得初始快照。
3. 当前渲染宽高、DPR、预览模式或用户覆盖变化时重新评估布局。
4. 只在最终布局模式或相关布局参数变化时更新控件，避免每帧重建 UI。
5. 刷新所有依赖此快照的组件，不只刷新中央判断函数。

可以缓存稳定的平台身份；窗口尺寸、DPR、模拟设置与最终布局不能无条件永久缓存。

若通过每帧轻量比较实现变化检测，应交给项目既有主更新流程统一驱动，不额外注册会与入口冲突的更新订阅。

### 4. 输入保持兼容，提示可以随实际操作切换

- 鼠标、触摸和键盘可以同时可用。
- 根据实际输入切换键位提示或触摸提示，而不是直接改写硬件身份。
- 长按、悬停、右键等交互应有清晰的兼容策略与触摸替代路径。
- 手机布局不应妨碍外接键盘，电脑布局也不应妨碍触屏操作。

### 5. 安全区独立处理

真实安全区、宿主菜单覆盖区、普通视觉留白是三个不同概念。

优先使用环境确实提供且已验证的安全区信息；没有可靠信息时使用保守留白，并注明它是估算。不要因为判为移动端，就假定统一的固定边距一定安全。

## 六、验证矩阵

| 测试场景 | 要验证的重点 |
|----------|--------------|
| Android / iOS / HarmonyOS 原生运行 | 平台身份识别、实际宿主覆盖层、输入事件 |
| 原生平板 | 移动平台身份与宽屏布局能否分离 |
| 手机 Web：DPR 1、2、3 | 不满足兜底时是否能手动选择合适布局 |
| 桌面 Web：高 DPR 小窗口 | 是否被尺寸启发式误认为手机 |
| Windows / macOS 高 DPI 小窗口 | Web 兜底不能影响原生桌面身份 |
| 桌面触屏 | 真实触摸可用，但平台身份仍是桌面 |
| 手机外接键盘 | 移动端布局下键盘操作正常 |
| 启动后切换预览设备或触摸模拟 | 中央快照与战斗 UI 局部参数同步更新 |
| 横竖屏切换、窗口缩放、DPR 变化 | 布局更新而不丢失对局状态 |
| 已保存的用户缩放与换手设置 | 默认策略不能覆盖用户选择 |

诊断日志至少记录：平台、宽高、DPR、逻辑短边、触摸模拟、最终布局与命中原因。仅在启动或环境变化时输出，避免逐帧刷屏。

本次结论来自静态代码研究，未完成上述实机测试；现有问题应称为代码可推导的风险，不应声称已经在全部设备上复现。
