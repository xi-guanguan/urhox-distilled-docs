# 大结构数据压缩与迁移升级方案

本文用于背包、天赋、收藏、装备词条、任务集合等可能增长的数据。目标是降低存储和同步体积，同时保证语义不变、迁移可重试、断线不回档。文中的 `RecordListCodec`、`BitsetCodec`、`SnapshotCodec`、`ChunkedCodec` 是可组合的设计模式，不是必须新增的固定类名。

## 一、现有能力基线

### 背包

当前压缩链路是：业务记录 -> 可定制的 `RecordListCodec` -> 版本化字符串 -> `serverCloud.list`。`RecordListCodec` 只是推荐模式名，具体业务可以使用自己的模块名。

- 快照头：`I2|configVersion`。
- 装备记录：`E3`，包含实例 ID、模板/品质短码、等级、flags、固有值、普通词条和武功词条。
- 堆叠物品：`S2`，包含物品短码、数量和 flags。
- `M2` 是初始化 marker，用于防止空列表重复 seed。
- ID 和数值使用稳定短码/base36，增删改通过 `ListAdd/ListModify/ListDelete` 的 BatchCommit 完成。
- 云写失败时，内存记录和客户端 snapshot 都保持上一次成功版本。

### 天赋

当前压缩链路是：布尔/解锁 ID 集合 -> 可定制的 `BitsetCodec` 按稳定索引建 bitset -> Base64 -> 版本化字符串。`BitsetCodec` 只是推荐模式名，具体业务可以使用自己的模块名。

- N 个节点占 `ceil(N / 8)` bytes。
- 200 节点示例为 25 bytes、36 字符 Base64、总长 39 字符。
- 解码会校验版本、Base64 和字节长度。
- 运行时可回退到中心节点，但迁移阶段必须把失败视为待处理数据，不得静默丢弃解锁进度。

### 尾写保底

持久化域使用 revision 和 detached 队列：保存中产生的新修改排队为最新 snapshot；断线时先捕获 dirty snapshot，再尝试主保存；主保存失败进入 detached 重试；重连加载会等待尾写完成，避免读到旧云快照。当前配置为最多 3 次尝试，退避序列为 1/3/9 秒，耗尽返回显式错误。

## 二、迁移前的不可变原则

1. 压缩只改变表示，不改变业务语义、排序、数量、装备状态、解锁节点和持久化生命周期。
2. 旧格式必须可读；新格式写成功且校验通过前，不得删除旧数据。
3. 每次转换必须带格式版本、配置版本或 codec 版本，禁止依赖字段猜测。
4. 迁移写入必须走 revision/尾写队列，不能绕过 PDM 直接写云端。
5. 失败要可重试、可观测、可回滚；不能把“解码失败”当成空数据。

## 三、推荐升级路线

### 阶段 0：只读盘点

- 统计旧格式记录数、最大结构大小、损坏记录、未知 ID、重复 ID 和缺失配置引用。
- 估算压缩前后长度及是否可能超过 64KB。
- 生成迁移报告，不写入线上数据。

### 阶段 1：兼容读取与纯函数转换

- 保留 `DecodeLegacy`，新增 `EncodeVn/DecodeVn`，两者都返回明确错误码。
- 转换过程只做内存操作：旧值 -> 规范记录 -> 新编码。
- 对转换前后的业务语义做校验：记录数量、ID 集合、数量、装备 flags/词条、天赋解锁集合、积分等必须一致。
- 为每个 codec 添加 round-trip、未知版本、非法长度、未知引用、重复 ID 和边界大小测试。

### 阶段 2：影子编码

- 正常读取旧格式，同时在内存生成新格式并计算语义 hash/摘要。
- 只记录压缩比和校验差异，不切换读取来源。
- 对超大结构提前进入 chunk 方案，避免先写入单个 `SetVar` 再补救。

### 阶段 3：双读单写 / 惰性迁移

1. 读取优先新格式，缺失时读取旧格式。
2. 旧格式成功解码后立即转换新格式。
3. 新格式保存成功后重新解码并做语义校验。
4. 校验成功后记录迁移版本；旧数据暂不删除。
5. 同一玩家并发请求必须由 uid/domain 或 uid/collection 串行化，避免两个迁移互相覆盖。

背包建议优先使用新 list key 或带版本的 marker 完成一次完整写入，再切换 active key；不要在同一列表中混合无法区分的旧记录和新记录。天赋可以复用同一字段，但必须先支持旧 map/table 读取，再写入 `T1:` 编码。

### 阶段 4：批量回填

- 按玩家分批、限速、可暂停执行。
- 每个玩家只处理一次成功的版本跃迁，重复执行必须幂等。
- 每批记录成功数、失败码、平均压缩比、最大 payload 和尾写重试次数。
- 失败玩家保留旧格式并进入重试队列，不阻塞全局批次。

### 阶段 5：切换与清理

- 新格式覆盖率和校验成功率达到目标后，切换默认读取路径。
- 保留旧数据至少一个回滚窗口；期间仍保留旧格式读取器。
- 回滚窗口结束后再删除旧 key/旧字段，并先做最终备份和抽样恢复演练。

## 四、背包迁移细节

旧 JSON/对象列表迁移为压缩记录时：

1. 规范化 `kind/id/itemId/templateId/qualityId/quantity/affixes/flags`。
2. 校验数量非负、实例 ID 唯一、短码映射无冲突、词条引用存在。
3. 生成 `E3`/`S2` 记录并写入新 list；全部成功后写入 `M2` marker。
4. 重新读取新 list，解码并与旧记录做语义比较。
5. 比较成功才发布 REPLICATED snapshot；失败只保留旧状态。

如果使用分块 snapshot，meta 至少包含 `version/configVersion/chunks/total/checksum`；客户端必须拒绝缺块、重复块和 checksum 不匹配。

## 五、天赋迁移细节

1. 将旧的 `{ nodeId = true }`、数组或稀疏表规范化为解锁 ID 集合。
2. 对每个 ID 按当前 `nodeOrder` 找 index；未知 ID 进入错误报告，不能直接丢弃。
3. 生成 `T1:` bitset，写入持久化域并保留原始快照。
4. 解码新值，比较解锁集合和天赋点/已消费点数。
5. 校验成功后再把迁移 revision 标记为完成。

节点顺序一旦用于线上编码就必须稳定。若必须调整顺序，应发布新的 codec 版本和显式映射迁移，不能直接重排 `nodeOrder` 后继续使用 `T1`。

## 六、尾写与回滚要求

- 迁移保存必须记录 `migrationRevision`，并与 PDM 的 `dirtyRevision` 单调关联。
- 主保存进行中若业务再次修改，迁移 snapshot 只能作为待写快照，不能覆盖更新后的业务 snapshot。
- 断线时先把包含新格式的最新 snapshot 放入 detached 队列，再清理节点。
- 重连时先等待 detached save；尾写失败或重试耗尽时返回显式错误并阻止旧快照 hydrate。
- 新格式校验失败、主写失败、尾写失败时，读取旧格式继续服务，并保留迁移失败原因。
- 未完成“新写成功 + 语义校验 + 尾写完成”的迁移，禁止删除旧数据或切换 active key。

## 七、验收清单

- [ ] 新旧格式 round-trip 通过。
- [ ] 旧数据未知 ID、损坏记录、版本不支持都有明确错误码。
- [ ] 背包数量、装备状态、词条、天赋解锁集合和积分语义一致。
- [ ] 最大结构不会触发 64KB 单帧限制，必要时已分块。
- [ ] 写失败不会更新内存快照或客户端快照。
- [ ] 保存中产生的新 revision 会继续写入最新 snapshot。
- [ ] 断线主写失败会进入 detached 重试，重连不会读旧云快照。
- [ ] 重试耗尽会显式失败，并保留旧格式可回滚。
- [ ] 批量回填可暂停、可重试、可统计，且重复执行幂等。
- [ ] 回滚演练完成后才清理旧格式。
