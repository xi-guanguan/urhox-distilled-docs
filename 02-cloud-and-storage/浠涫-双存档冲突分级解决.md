# 双存档冲突分级解决（本地 + 云端）

> **这是什么**：单机游戏同时存在本地与云端两份有效存档时，如何决定用哪一份。核心是**按玩法进度的差异大小分级**——差异小自动取较新，差异大才让玩家选，并保证未决期间绝不写盘。
>
> **原作者**：浠涫（《包租婆：这把赚翻了》）
> **推荐度**：L1（已在真实项目实现并跑通 15 项回归；跨设备真机分歧未验收，见文末边界）
> **适用场景**：使用本地 File + clientCloud 双通道存档的单机/弱联网游戏。已有云端存档、准备加本地备份，或现有"取最新"策略被玩家反馈丢过进度的项目。
>
> **同类对比**：
> - **特色**：不引入新的存储层，只在既有双通道的**合并点**加一层分级判定；判定维度是玩法进度（通关次数/解锁层/是否在局中），不是文件差异或时间戳
> - **优点**：差异小时不打扰玩家（多数冲突场景），差异大时绝不替玩家做决定；未决期间拒绝一切写入，从机制上杜绝静默覆盖
> - **缺点**：不做 merge，两份分歧时只能二选一；依赖存档带 `savedAt`（旧档缺失时退化为 0，仍可工作）；未加内容校验和

---

## 一、问题：时间戳不是权威

双通道存档在启动时可能同时读到两份**都有效**的记录：

```
本地 File  ─┐
            ├─→ 哪一份才是玩家的进度？
云端 value ─┘
```

两种常见做法都有缺陷：

| 做法 | 问题 |
|------|------|
| **按时间戳/seq 取最新** | 假设"新"等于"好"。但两份可能是**不同分支的进度**，丢掉哪份都是玩家的损失 |
| **云端优先** | 换设备/重装后云端旧档顶掉本地新进度；离线期间的进度直接消失 |

**共同缺陷**：用一条规则替代了玩家的判断。当两份差异很大时，那不是"哪个更对"的技术问题，而是"你想保留哪段进度"的产品问题——只有玩家能回答。

> **与"乐观锁 seq 大者胜"的关系**：乐观锁解决的是**并发写覆盖**（同一份数据被两个写入者竞争），前提是两边在写同一段进度。而双存档冲突的前提恰恰相反——两边可能是**不同的进度分支**。seq 更大只说明"写入更晚"，不说明"更该保留"。两者要解决的问题不同，不要混用。

## 二、方案：按差异大小分级

核心是把冲突分成两类，**只在真正需要时才打扰玩家**：

```
两份存档都存在
      │
      ├─ 差异不大 ──→ 静默取较新（不打扰）
      │
      └─ 差异很大 ──→ 弹窗列出两份，让玩家选
                        （两边都不删，选完互相同步）
```

既避免"每局都弹窗"的骚扰，也避免"静默顶掉一段进度"的伤害。

### 2.1 什么算"差异很大"

判定必须**用玩家真正在乎的进度维度**，而不是内部字段：

| 维度 | 判定 | 理由 |
|------|------|------|
| 通关次数 `wins` | 任一不同即算大差异 | 核心成就，差一次都不能替玩家放弃 |
| 最高解锁层 `highestFloor` | 任一不同即算大差异 | 进度解锁只增不减，差异不可逆 |
| 是否持有进行中的租约 `run` | 有无不同即算大差异 | 一边在局中一边不在，是两条不同的游玩轨迹 |
| 同一局内的期数 `period` | 差 ≤2 视为小漂移 | 同一局内的正常推进，不值得打断 |

前三条是"硬差异"，最后一条是唯一允许自动合并的"软差异"。

### 2.2 判定实现（纯函数，无副作用）

```lua
-- 只用于展示与比较的进度摘要。绝不作为规则输入。
function Save.Describe(data)
    if type(data)~='table' then return nil end
    local profile=data.profile or data.game and data.game.profile
    local game=data.game
    local summary={revision=data.revision or 0,savedAt=tonumber(data.savedAt) or 0}
    if type(profile)=='table' then
        summary.wins=tonumber(profile.wins) or 0
        summary.floor=tonumber(profile.highestFloor) or 1
    end
    if type(game)=='table' then
        summary.run=true
        summary.runFloor=tonumber(game.floor) or summary.floor or 1
        summary.period=tonumber(game.period) or 1
        summary.phase=tostring(game.phase or '')
    end
    return summary
end

-- 变化不大 → 可以静默取较新
function Save.Similar(a,b)
    if type(a)~='table' or type(b)~='table' then return false end
    if math.abs((a.wins or 0)-(b.wins or 0))>0 then return false end
    if math.abs((a.floor or 1)-(b.floor or 1))>0 then return false end
    if a.run~=b.run then return false end
    if a.run then
        if a.runFloor~=b.runFloor then return false end
        if math.abs((a.period or 1)-(b.period or 1))>2 then return false end
    end
    return true
end
```

**要点**：`Describe` 只读不写，`Similar` 是纯比较。两者都不接触存储，可以被 UI 单独调用做展示。这让"判定逻辑"和"存储逻辑"解耦，也让判定可以独立测试。

### 2.3 存档要带时间戳

时间戳**不再用于决定谁赢**，只用于两件事：

1. 在两份存档之间**指出哪份更新**（给玩家做判断的参考）
2. 差异不大时，决定取哪一份

```lua
return {version=1,revision=Save.revision+1,savedAt=os.time(),...}
```

旧存档没有该字段 → 按 `0` 处理，自然落进"较新"比较。**不做迁移，也不需要迁移**，因为缺失只是让时间戳比较退化，不影响任何正确性。

## 三、加载流程

```
Load()
  │
  ├─ 解析本地（含 .bak 备份，取 revision 较高者）
  ├─ 解析云端（异步）
  │
  └─ resolve(本地, 云端)
        │
        ├─ 只有一边有 ──────→ 直接用
        │
        ├─ 两边都有 且 Similar ──→ 按 savedAt 取较新
        │                          （完全打平保留云端，见下）
        │
        └─ 两边都有 且不相似 ──→ 不写任何一边
                                  置 conflict = {localSave, cloudSave, ...}
                                  回调 reason = 'save_conflict'
```

合并点实现：

```lua
local function resolve(localData,backupData,localError,backupError,cloud,cloudError)
    local localPick=localData
    -- 本地主档与 .bak 取 revision 较高者，抗半截写入
    if backupData and (not localPick or (backupData.revision or 0)>(localPick.revision or 0)) then
        localPick=backupData
    end
    Save.cloudLoadError=cloudError
    Save.localCandidate=localPick or nil
    Save.cloudCandidate=cloud or nil
    Save.cloudWriteBlocked=cloudError~=nil

    if not localPick and not cloud then finish(nil,localError or backupError or cloudError);return end
    if not localPick then finish(cloud);return end
    if not cloud then finish(localPick);return end

    local localAt,cloudAt=tonumber(localPick.savedAt) or 0,tonumber(cloud.savedAt) or 0
    local sameProgress=Save.Similar(Save.Describe(localPick),Save.Describe(cloud))
    -- 完全打平保留云端：它是跨设备权威。
    local localNewer=localAt>cloudAt or (localAt==cloudAt and (localPick.revision or 0)>(cloud.revision or 0))

    if sameProgress then
        Save.localBaseRevision=localPick.revision or 0
        Save.cloudBaseRevision=(localNewer and localPick or cloud).revision or 0
        finish(localNewer and localPick or cloud)
        return
    end

    -- 真实分歧：两边都留着，交给玩家。
    Save.conflict={localSave=localPick,cloudSave=cloud,localAt=localAt,cloudAt=cloudAt}
    finish(nil,'save_conflict')
end
```

**完全打平时保留云端**——这是原有契约（跨设备权威）。保留它，因为该分支只在"时间戳和 revision 都相同"这种极罕见情况下触发，此时两份内容高度一致，选哪份都不构成损失。

### 3.1 最要紧的一条：未决期间绝不写盘

这是整个方案的安全边界。如果玩家还没选，自动保存一旦触发，就会把当前内存状态写到某一侧，**静默覆盖掉玩家还没看到的那份存档**——方案的意义完全丧失。

所以所有写入口和开局入口全部加门控：

```lua
function Screen:Save(done)
    if self.transient or self.workbench then return false end
    -- 未决冲突下不自动保存，避免覆盖任一候选
    if self.saveConflict then return false end
    ...
end

function Screen:NewGame()
    if self.saveConflict or not self.loaded or self.loadError or self.store.loadBlocked then return false end
    ...
end

function Screen:Resume()
    if self.saveConflict or not self.loaded or self.loadError or self.store.loadBlocked then return false end
    ...
end
```

**注意 `NewGame`/`Resume` 也要门控**——否则玩家在冲突弹窗下点了"开间新房"，会用全新存档覆盖掉那份还没看的记录。这是容易漏掉的一处。

## 四、选择界面

弹窗列出两份，每份只显示玩家能理解的进度：

```
┌─────────────────────────────────────┐
│       两份存档进度不一致             │
│  选一份继续。没选中的那份不会被删除。 │
├─────────────────────────────────────┤
│ 本地存档                             │
│   通关 2 次 · 最高第 3 层            │
│   进行中：第 3 层 · 第 4 期          │
│   09月24日 15:46                     │
│            [ 用这份 ]                │
├─────────────────────────────────────┤
│ 云端存档                     较新    │
│   通关 7 次 · 最高第 9 层            │
│   当前没有进行中的租约               │
│   09月24日 18:33                     │
│            [ 用这份 ]                │
├─────────────────────────────────────┤
│    两边都会同步为你选的那份          │
└─────────────────────────────────────┘
```

三个设计要点：

1. **只说玩家在乎的**——通关次数、最高层、当前局进度、保存时间。不显示 revision、hash 这类内部字段。
2. **明确"不会删除"**——玩家最怕"选错了另一份就没了"。文案直接写明，降低决策压力。
3. **标出哪份更新**——"较新"只是参考信息，不是预选项，避免玩家无脑点。

选择后，两份存档**收敛**到玩家选的那一份：

```lua
function Screen:ChooseSave(side)
    if not self.saveConflict then return false end
    local chosen=self.store.ResolveConflict(side)
    if not chosen then return false end
    self.saveConflict=nil
    self:ApplyLoaded(chosen,nil,self.store.revision,nil)
    -- 让另一通道也收敛到玩家的选择。失败不能撤销已完成的加载，
    -- 只通过常规保存提示暴露。
    if self.loaded then self:Save() end
    return true
end
```

`ResolveConflict` 同时把 `localBaseRevision` 与 `cloudBaseRevision` 都设为选中记录的 revision，这样下一次保存会同时写两侧，完成收敛。

## 五、与同类方案对照

调研过几个开源存档工具，它们处理冲突的方式各不相同：

| 项目 | 语言 | 冲突处理 | 与本文方案的关系 |
|------|------|---------|----------------|
| [Kiowx/save_manager](https://github.com/Kiowx/save_manager) | Python | 本地与云端都变化时**保留冲突并要求用户选择**，不盲目覆盖 | **思路最接近**：都拒绝静默覆盖。差别在于它面向 PC 存档管理（多游戏、文件级），本文是游戏内嵌的双通道存档，判定维度是**玩法进度**而非文件差异 |
| [mtkennerly/ludusavi](https://github.com/mtkennerly/ludusavi) | Rust | 备份/恢复为主，冲突靠人工选择备份点 | "多版本备份"模型，天然保留所有历史，等于回避了冲突问题 |
| [mcthesw/game-save-manager](https://github.com/mcthesw/game-save-manager) | C# | 跨平台 GUI 存档管理 | 面向本地备份，不处理云同步冲突 |
| [SteamCloudFileManager](https://github.com/Fldicoahkiin/SteamCloudFileManager) | Rust | 树状视图手动上传/下载 | 完全交给用户手动操作，没有自动化策略 |
| [OpenCloudSaves](https://github.com/DavidDeSimone/OpenCloudSaves) | — | 跨平台同步 | 已停用 |

**共同点**：凡是认真处理冲突的工具，都不会用"时间戳较新"单条规则自动覆盖——要么保留全部版本，要么让用户选。

**本文方案的差异**：多数工具的"选择"是**每次冲突都问**，因为它们面对任意文件差异，无法判断哪边更重要。而游戏存档有明确的**进度语义**，可以据此分级——差异小就自动合并，只在真正分歧时打断玩家。这是内嵌存档相对于通用存档管理工具的优势。

## 六、边界与未验收项

诚实说明这套方案**没有**覆盖的部分：

- **真机跨设备分歧未验收**。测试用的是私有内存/原生文件/云回调替身，造不出真实双端分歧。真实云端行为（延迟、部分写入、并发覆盖）未验证。
- **不做合并（merge）**。两份差异大时只能二选一，没有"把两边进度合起来"的能力。这是有意为之——合并游戏进度需要领域知识，且容易产出玩家没预期过的状态。
- **时钟依赖未消除**。`savedAt` 用 `os.time()`，设备时钟被改会污染"哪份更新"的提示。但因为时间戳只用于**提示**和**小差异时的取舍**，不用于"大差异"判定（大差异由 `wins`/`floor`/`run` 决定），时钟污染不会导致进度被静默顶掉——最坏情况只是时间提示不准，仍需玩家自己选。
- **未加校验和**。当前未对存档内容做完整性校验。损坏检测依赖 JSON 解码失败。这是后续可补的点。
- **阈值是项目特定的**。"期数差 ≤2"是《包租婆》的节奏决定的，换项目需要按自己的局长度量调整。`wins`/`floor`/`run` 这类"硬差异"的零容忍则可以通用。

## 七、实现清单

| 文件 | 职责 |
|------|------|
| `Save.lua` | `Describe`/`Similar` 判定；`Load` 的 `resolve()` 分级；`ResolveConflict` 采纳选择 |
| `SaveConflict.lua` | 冲突弹窗绘制与两个选择按钮（纯展示，不写盘） |
| `Screen.lua` | `saveConflict` 状态；`ApplyLoaded` 复用；`ChooseSave` 收敛；写入口与开局入口门控 |
| 回归测试 | 15 项：静默合并、各维度差异判定、两边保留、不写盘、选择采纳、未决拒写、UI 门控 |

回归覆盖的关键断言：

```
✅ 进度接近 → 静默取较新，不弹窗
✅ wins 不同 → 弹窗
✅ highestFloor 不同 → 弹窗
✅ 租约有无不同 → 弹窗
✅ 同租约 period 差 ≤2 → 静默
✅ 同租约 period 差 >2 → 弹窗
✅ 只有一边有 → 直接加载，不弹窗
✅ 分歧时两边都不写
✅ 未决期间拒绝一切写入
✅ 选择后两通道基线同时采纳
```
