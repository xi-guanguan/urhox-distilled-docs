# TapTap 单机客户端云存档修复与迁移指南

> **这是什么**：从一次单机客户端云存档修复中提炼的诊断与迁移流程，覆盖身份、读取、异步写入、未知结果、冲突恢复、本机 journal、UI 与验证边界。
>
> **原作者**：原素材未署名；用户提供，xi-guanguan 提交入库，Codex 整理。
> **推荐度**：L2（参考学习）。来源案例记录了代码回归与预览改善，但迁移需要重新核对目标 kit、schema 和接口；真实刷新持久化、切号及跨设备时序未全部验收。
> **适用场景**：TapTap 制造 / UrhoX Lua 中使用 `File` 与 `clientCloud` 的单机或弱联网进度存档，出现丢档、切号串档、写入超时后停写、冲突选择失效或本机写失败时。
>
> **同类对比**：
> - **特色**：在[店长的 clientCloud 接入方案](店长-clientCloud云存档系统实现指南.md)和[糖心哥的加载失败保护](糖心哥-云存档加载失败防护指南.md)之外，细分 queued / sent / unknown，保留不可变请求证据，并覆盖 A→B→A、迟到回包与两银行部分写失败。
> - **优点**：与[浠涫的双存档冲突分级](浠涫-双存档冲突分级解决.md)形成互补，明确区分玩家选档、远端读回观察和真实请求确认；不以 revision 更大、正文相同或读取失败为覆盖授权。
> - **缺点**：不是可直接安装的完整控制器；来源参数、软进度合并规则和 Lua 5.4 ID 边界均需适配。未提供设备锁、CAS、跨设备事务或高风险权益的可信结算协议。
>
> **整理日期**：2026-11-01。

本文保留完整诊断提示词、接口片段、异常时序、回归清单和已知缺口，供其他项目的开发助手先诊断，再按该项目的数据与接口做最小修复。它不是引擎内置存档库，也不是可以原样覆盖所有项目的通用脚本。

## 1. 可以直接复制给其他项目助手的任务提示词

```text
请修复本项目的单机客户端云存档，参考所附《TapTap 单机客户端云存档修复与迁移指南》。

先沿真实入口检查整个用户代码中的存档链路：账号取得、初始读取、校验、应用、修改、
本机保存、云提交、冲突选择、重试、切号、退出和 UI。不要只改“已同步”的提示文字。

先使用目标项目可用的 @tianyi_game-save，核对该项目官方文档、类型声明和部署接口。
先判断当前单机/多人配置，沿用既有架构；不要因为存档故障而新增服务端、另建认证或改联机模式。

列清当前 owner、云 key、本地路径、旧格式、实际保存字段和保存触发点。
必须保留原账号归属、原 key 和有效旧档；错误、损坏、未来版本不能当成新玩家。
不要复制来源项目的 devour2048 key、配饰 schema 或最高分合并规则到本项目。

重点排查：
1. 数字/字符串/整值浮点 userId 比较，以及超精度 ID 是否已丢失信息；
2. 昵称查询与进度同步是否独立，是否错误地用本机名字冒充平台昵称；
3. 云读成功但本机 IO 失败后，默认数据是否反向污染已读取的云档；
4. 排队但未发送的写、真正发送的写、结果未知的写是否混为一谈；
5. 深快照、保存期间新修改、重复/迟到回包和 A→B→A 是否正确隔离；
6. 冲突选择是否重新读取基线，失败后能否再次选择；
7. 未知写是否有保留证据、玩家明确取舍的恢复出口；
8. 本机部分写失败是否保全最后好档，重试是否有明确授权；
9. 旁路成绩/局数报告失败是否无条件冻结主进度；
10. UI 是否准确区分本机保存、云提交、读回观察和结果未知。

先用 mock 测试异常时序，不直接操作正式玩家云档，不清档、不重置、不发布。
对可回滚的单机软进度，冲突时可保留双方候选，交由玩家明确选择当前设备继续。
选择不取消旧请求，也不提供设备锁；付费权益、增量领取、交易不能套用这种覆盖恢复。

修复应保留正常自动保存，不要每次保存都弹确认；对冲突或未知恢复才明确提示取舍。
只读轮询不能重建正在进行的世界，也不能按 revision 大小自动选胜者。

修改 Lua 后先通过 LSP Error 检查，再执行官方 build。
交付时列出根因、修改文件、保留格式、已测/未测和仍未覆盖的边界。
不要把 mock 或无登录离屏验证说成真实登录、刷新持久化或跨设备同步验收。
```

## 2. 先分清：究竟是哪一类“没读到存档”

| 现象 | 先检查 | 不要直接下的结论 |
|---|---|---|
| 云档已同步，但没有昵称 | 独立昵称接口、当前账号、回包 ID 和昵称状态 | “云存档没接好”或“把本机名字显示出来即可” |
| 历史最佳保留，新局回到初始值 | 实际保存范围、单局初始化逻辑 | “一定丢档” |
| 换配饰/静音后刷新回默认 | 修改钩子、本机 IO、profile 内容、同步是否完成 | “加一条 Set 就够了” |
| 一次超时后永久不能保存 | pending、重试语义、是否缺恢复出口 | “清 pending 再重发” |
| 选择本机/云端后按钮一直灰 | loading→conflict/read-error/unknown 的 UI 解锁 | “网络还没恢复” |
| 换账号后看到上个账号进度 | owner、目标记录、旧回包和缓存隔离 | “给所有玩家共用一个本地文件” |
| 首次写失败后每次都失败 | 两银行状态、部分坏文件、创建授权 | “删掉所有本地档” |

**最重要的区分：账号元进度，不等于未结束的单局现场。**

来源项目保存历史最佳、已拥有配饰、当前配饰、静音、上局成绩和累计局数；没有保存蛇身、位置、散块、AI 决策、随机状态等现场。因此历史最佳为 262K、普通新局从 2 开始可以同时成立。

其他项目若要求“退出后继续上一局”，必须单独设计完整现场 schema、恢复时机与版本兼容，不能仅凭账号 profile 就宣称实现续局。

## 3. 接入前必须建立的数据清单

在目标项目中填写，不要跳过：

| 项目 | 需要记录的事实 |
|---|---|
| 真入口 | 哪个 `Start()` 创建控制器；是否有加载页/预加载延迟 |
| 当前模式 | 单机还是已有多人；当前部署配置与代码一致吗 |
| 账号来源 | 当前客户端实际提供的 `clientCloud.userId`；何时有效 |
| 主进度 | 原云 key、数据域、封套版本、owner、实际字段 |
| 旁路数据 | 排行榜、局数等是报告，还是影响玩法的权威数据 |
| 本机存储 | 当前路径、账号隔离、旧档来源、最后好档保护 |
| 修改来源 | 开局、结算、装备、静音、检查点、奖励、迁移 |
| 应用来源 | 读档/玩家选择后如何更新活数据、世界、UI 与奖励回调 |
| 退出行为 | 是否只调用保存；不能承诺退出时异步云请求必然完成 |
| 部署证据 | 当前 kit 的接口与文件系统行为；不能以最新源码替代实测 |

### 来源项目的路径与 key：仅用于理解案例

- `devour2048_profile_v1`：完整账号进度，`values` 数据域。
- `devour2048_best_v1`：历史成绩，`iscores` 数据域。
- `devour2048_games_v1`：绝对局数，`iscores` 数据域。
- `devour2048-account-<owner>.0.json` / `.1.json`：本机两银行 journal。
- `cubes2048-save.json`：无账号归属的旧本机档，保留原文件、不直接覆盖。
- `devour2048-controls.json`、`devour2048-audio.json`：独立本机设置，不进入账号冲突合并。

**迁移到另一项目时保留另一项目自己的名字和格式。改 key 会读到另一份数据，不能把“新 key 缺档”当作原问题解决。**

## 4. 单机客户端的实际 API 分工

以下为来源项目已核对的接口调用形状；是接线片段，不是完整存档控制器。目标 kit 必须重新核对类型声明与回调约定。

```lua
-- 第一阶段：读取主进度及成绩报告。
clientCloud:BatchGet()
    :Key(PROFILE)
    :Key(BEST)
    :Key(GAMES)
    :Fetch({
        ok = function(values, iscores)
            -- values[PROFILE]：完整表封套。
            -- iscores[BEST] / iscores[GAMES]：整数报告。
            -- 先校验整个响应与封套，再决定缺档、应用或冲突。
        end,
        error = function(code, reason)
            -- 读取错误不是缺档；不创建默认云档覆盖。
        end,
        timeout = function()
            -- 未取得结果；保留本机候选，不把读取失败当成功。
        end,
    })

-- 第二阶段：由同一目标的串行写调度调用，而非到处直接写。
clientCloud:Set(PROFILE, immutableEnvelope, writeEvents)
clientCloud:SetInt(BEST, math.floor(bestReport), writeEvents)
clientCloud:SetInt(GAMES, math.floor(absoluteGames), writeEvents)

-- 平台昵称是独立查询，不属于存档字段。
GetUserNickname({
    userIds = {currentOwner},
    onSuccess = function(items)
        -- 本项目回包项使用 userId / nickname。
        -- ID 规范化后，只接受请求范围内的真实公开昵称。
    end,
    onError = function(code, reason)
        -- 单独显示昵称失败，不伪造成功，不影响主进度的独立状态。
    end,
})
```

来源项目排行榜使用 `GetRankList(BEST, 0, 50, false, events)`、`GetRankTotal(BEST, events)` 和 `GetUserRank(clientCloud.userId, BEST, events)`。对应成功回调分别为排行榜项数组、`(total)`、`(rank, scoreValue)`；本项目排行榜项使用 `userId` 与 `iscore[key]`，不要照抄旧示例中的其他字段名。

注意：

- 主进度、最佳成绩和局数分别提交，不是跨三个 key 的原子事务；不能把其中一个 key 成功当成全部成功。
- `Set` 的完整表与 `SetInt` 的整数报告不能混用。
- 局数当前是绝对值报告，不是 `Add` 增量；未知请求不能无去重依据地重复增量。
- 昵称到达顺序与云档到达顺序不保证一致；两者应有独立请求通道和 UI 状态。
- `-429` 不应未经接口证据就解释成“限流”。来源项目将其保留为有界诊断码，不把任意 SDK 原文、账号数据或存档正文写进日志。
- 普通 `clientCloud` 不提供可信成绩认证、CAS、分布式锁或跨设备事务。

## 5. 修复点一：统一账号 ID 和整值数字

### 5.1 ID 展示格式不能参与身份比较

原问题示例：

```lua
-- 同一个账号的不同 Lua 数值类型/回包形式：
local a = "12345678"
local b = 12345678.0
-- 直接 tostring(b) 可能得到 "12345678.0"，与 a 不相等。
```

建立一个 ID 规范化入口，并用于账号、昵称回包、请求允许集合、缓存与排行榜行，不要只修一个比较位置。

来源项目的边界参考：

```lua
local MAX_EXACT = 9007199254740991

local function normalizeId(id)
    if type(id) == "number" then
        if id ~= id or id <= 0 or id % 1 ~= 0 then return nil end
        if math.type(id) ~= "integer" and id > MAX_EXACT then return nil end
        return tostring(math.floor(id))
    end
    if type(id) == "string" and id:match("^[1-9]%d*$") and #id <= 20
        and (#id < 20 or id <= "18446744073709551615") then
        return id
    end
    return nil
end
```

前提与限制：

- 这是 Lua 5.4、正 uint64 十进制 ID 的案例边界，其他身份格式应按真实接口调整。
- 大 ID 字符串不转 `tonumber`；已经以不精确浮点数传入的 ID，不能靠格式化恢复原值，应拒绝并排查宿主协议。
- 不合成正式账号、不猜另一个 SDK 的身份，也不把离屏验证替身当作真实账号。
- 账号没拿到时必须显示真实状态；不能用固定 ID 来“让云档能跑”。

### 5.2 整值配饰编号也有同类问题

已校验 `skin` 为合法整数值后，`3.0` 对应的拥有集合 key 应是 `"3"`，不是 `"3.0"`：

```lua
-- 前面必须先验证：数字、有限、整数值、在合法编号范围内。
local ownedKey = tostring(math.floor(save.skin))
local equippedIsOwned = save.owned[ownedKey] == true
```

不能把这一修复扩展成随意截断非法小数；`3.7` 应拒绝，不是偷偷变成 `3`。

## 6. 修复点二：云候选与活数据始终一致

错误时序：

```text
云读到合法的配饰/静音/局数
  → 更新控制器 record
  → 本机写失败，提前 return
  → 活游戏 save 仍是默认值
  → 玩家下一次修改，把默认偏好写回 record
```

修复原则：

1. 云响应与候选必须完整通过 schema 校验。
2. 将合法候选同步到同一份活数据，再进行后续本机写确认。
3. 本机写失败仍显示未保存，暂停云提交，不能宣称成功。
4. 期间玩家的新修改仍更新当前记录；重试保存最新记录，不能回灌旧默认值。
5. 玩家明确选档时，先在副本组装候选并落盘；失败恢复原 record/pending 对象引用，不释放原屏障。
6. 原来的异步奖励/广告/旧账号回调不能污染新应用的进度。

**只读观察与真正应用必须分开。** 初始化或玩家选档可以应用；后台 verify/observe 不能反复重建正在玩的单局。

## 7. 修复点三：排队、发送、未知是不同状态

```text
dirty
  → queued（尚未交给 SDK）
  → 真正发送前，本机持久化不可变 pending
  → sent / syncing
      ├─ 真实成功回包：只确认 submittedRevision/saveId 对应快照
      └─ 超时或无法证明未提交的错误：unknown，保留 pending
```

实施要求：

- 捕获深快照，不把活 `save` 表直接传给异步请求。
- queued 阶段切号或主动重读，可以撤销未发送队列，保留 dirty；不能凭空制造远端未知写。
- 真正发送前，pending 必须先本机保存成功；失败就不调用云 SDK，并释放调度通道。
- pending 本机保存与 SDK 调用之间并非原子事务。崩溃后若无法证明是否提交，仍需保守处理，不能声称该窗口已完全消除。
- 发送成功期间新增的进度/嵌套配饰修改继续 dirty；旧成功只确认旧快照。
- 重复回包只处理一次；超时后一个真实迟到成功仍可确认原请求。
- A→B→A 不只比较当前 owner 字符串，还要隔离请求 epoch 与原目标记录。
- 旧请求可以更新原目标的确认事实，不能改新账号 UI、世界或新 pending。
- 读档/冲突选择受理时，撤销该目标尚未发送的旧写快照；对账后再捕获最新修改。

来源项目的调度参考值为：共享请求启动间隔 0.25 秒、写最小间隔 3 秒、应用 watchdog 12 秒、首次读取最多 3 次并按 3/6 秒退避、观察间隔 30 秒。这些是项目参数，不是官方统一额度，另一项目应按实际请求成本和接口限制配置。

## 8. 修复点四：未知写的玩家恢复出口

### 8.1 为什么“读到了同一个快照”仍不能直接清 pending

一次读回仅证明观察时云端内容与快照相同，不证明旧请求已结束、取消或不会迟到。超时后清 pending 并盲目重发，会放大时序问题；永久封写又让玩家无路可走。

### 8.2 本次采用的受控恢复流程

仅适用于业务允许回退的单机软进度：

1. 保留原 pending，包括 kind、revision、完整不可变 snapshot。
2. 重试只读取，取得合法本机/云端候选；云缺档也明确展示，不伪造一份云档。
3. UI 展示双方实际内容与取舍，允许玩家明确选择本机或云端。
4. 选择后重新读取；完整远端封套与刚才看到的基线不一致就重新选择。
5. 在副本上组装：双方备份、原未知证据、所选正文、新 base/revision。
6. 本机落盘成功后，才把原 pending 转入 unknownHistory 并开放后续新进度同步。
7. 本机落盘失败恢复原对象引用与原 pending；不发新云写。
8. 恢复后提交 profile，需要读回完整封套核对；后续只读观察不自动修复远端回退。
9. 旧回包只标记其历史请求获得真实确认，不清当前 pending、不替换新 base。

重读检查与下一次云写之间仍有并发窗口，并非原子比较后交换。`archive` 只保存最近一次候选对，未决请求另存在 `unknownHistory`；不能把它描述成无限版本历史或任意时间点回滚。

来源项目 unknownHistory 上限为 8 条。恢复时只移除已获得真实成功回包的历史项；满额且都是未决项时保留证据、停止再次解除屏障，不偷偷丢弃旧请求。

### 8.3 完整封套比较，不只是 data 相等

```text
data 相同，但 saveId/revision 不同
  ≠ 当前确认的同一个完整快照
```

在恢复后的冷启动、verify/observe、已发现不同候选后的迟到确认重读中，应比较完整 base。不要先按正文相等替换 base，再声称 verify 通过。

revision 是当前记录的版本信息，不是跨设备时钟；不能自动拿“revision 更大”的候选覆盖另一份。

### 8.4 成绩/局数报告的隔离

来源项目把主进度与旁路报告分开。未知 score/games 在玩家完成明确恢复后，只暂停对应未决 key 的报告，不永久冻结 PROFILE。迟到确认只能释放其对应证据。

这不是说未知报告可以一出现就忽略；未完成明确恢复前，原 pending 屏障仍在。

### 8.5 选择“本机/云端”的合并语义必须如实说明

来源项目不是所有字段纯替换：

| 字段 | 当前普通冲突选择行为 |
|---|---|
| 当前配饰、静音、上局成绩 | 跟随所选候选 |
| 历史最佳、累计局数 | 两份软进度取最大值，并结合独立读取的报告值 |
| 已拥有配饰 | true 项并集 |
| 本机 name | 保持本机字段，不冒充平台昵称 |
| 尚未归属账号的 legacy | 先明确归属；选择云端不会混入 legacy 成绩/配饰 |

这是一套既有游戏规则，不是通用冲突算法。余额、消耗品、体力结算、付费权益、退款、增量领取、交易不能直接套用 max/union 或覆盖恢复；应使用目标项目已核实的可信协议与去重依据。

**玩家选择接受单机进度可能回退，不等于取得独占设备写权，也不停止另一设备或旧请求。当前实现是显式取舍与检测，不是自动收敛协议。**

## 9. 修复点五：本机 journal 与部分写失败

### 9.1 两银行的核心规则

- 校验 owner、格式、sequence、完整 record。
- 读取最后有效银行；同 sequence 但正文不同属于冲突。
- 有未来版本时保护，不降级覆盖。
- 正常写另一个银行，关闭句柄后读回验证；失败保留最后好档。
- 写前再核对旧好档未改变，避免覆盖期间新出现的唯一好档。
- `FileExists=false` 只是一条文件观察，不是自动创建默认进度的业务授权。
- 原 legacy 保留；迁移在副本上进行，且明确旧档归属。

### 9.2 首次授权创建留下坏文件的安全重试

本次新增的是严格限定的会话内失败证据，不是任意坏档恢复：

```text
已明确授权首次 create=true
  → 本次写 .0 后留下不可解码坏 bytes
  → 本会话记录 owner / bank / path / 完整原始 bytes
  → 重试时原 bytes 未变，另一银行仍空
  → 写空 .1 并验证；保留坏 .0
```

边界：

- 原始 bytes 包括 `WriteString` 的终止字节及其后内容；只比较 `ReadString` 可能漏掉 NUL 后变更。
- 来源项目证据有界，最多 8 个 owner；满额不淘汰未决证据来授权新写。
- 未知来源坏档、重启后无本会话证据、未来版本、可解码不一致内容、bytes 改变、两银行都坏：拒绝自动创建/覆盖。
- 不因恢复失败删坏文件、重置全部档或写默认数据。
- 文件大小与证据上限是来源项目的保护边界，另一项目按真实 schema 设置。
- 两银行与读回验证并不提供跨设备云原子性，也不是文件系统 fsync 保证。

### 9.3 本地兼容性

来源项目云封套仍是 version=1，原 owner/key 未改；本机 v1 record 新增可选 `unknownHistory` 与 `recovering` 字段。

新版代码可以读取合法旧 v1 文件，但不意味着旧客户端能读取新版记录。旧白名单校验可能拒绝新字段，所以回滚客户端前要评估本地兼容，不能称为“双向兼容”。

## 10. 修复点六：UI 不能伪造保存成功或形成死路

| 状态 | 应传达的含义 |
|---|---|
| offline | 当前账号/云通道不可用；会话游玩不代表已持久保存 |
| loading | 正在读取，不覆盖；应有超时出口 |
| read-error | 未读到可信结果；不是新玩家、不是缺档 |
| invalid | 损坏或不兼容；保留现有数据，只重读不授权强覆盖 |
| local-error | 本机写未成功，云提交暂停；不能提示本机已保存 |
| conflict | 两份候选不同，等待明确选择 |
| pending | 本机已记录，仍待云同步 |
| syncing | 已提交，尚未取得云确认 |
| unknown | 原结果未知，保留证据；先读再明确恢复 |
| verifying | 读回核对恢复快照，不等于独占设备确认 |
| ready | 当前可确认的同步工作完成；若历史报告仍暂停，应另行提示 |

实施检查：

- `resolving` 不能只在成功回调中清理；loading 返回新 conflict/read-error/unknown 时也要解锁。
- invalid/busy 时不能授权选择覆盖；异常页面保留重读入口。
- 云端缺档时禁用“使用云端”，不能让按钮悄悄变成默认档。
- 未知恢复文案明确保留原证据、可能回退、不取消旧请求。
- localSaved=false 要显示刷新/退出可能丢失，不用“本机继续”掩盖未保存。
- nicknameStatus 独立；真实昵称没回来时显示中性占位，不使用可编辑本机旧名字冒充。来源项目正式入口传入 `requireAccountName=true`，移植时保留该接线，避免展示模块的兼容 fallback 分支改用本机名字。
- 正常自动/手动保存不额外弹确认；冲突、旧档归属和未知恢复才要求取舍。

## 13. 在另一项目中推荐的实施顺序

来源项目通过同一份共享 `save` 引用创建控制器，串接 `start()`、每帧 `update(dt)`、统一修改入口 `changed()` 和退出 `stop()`，并连接 `applied` 与状态通知去更新世界和 UI。单独复制 Store/CloudProfile/OnlineViews 三个模块、却遗漏真实入口接线，不构成完整修复。

1. **盘点，不动数据。** 写清真实入口、owner、key、路径、schema、保存范围及触发点。
2. **复现具体链路。** 先做 ID/回包、读失败、IO 失败、超时、切号与 UI 时序 mock。
3. **先修身份、校验和应用顺序。** 防止合法旧档被误拒或被默认值污染。
4. **修统一调度与深快照。** 区分 queued/sent/unknown，隔离旧回包，保留新 dirty。
5. **按业务设计取舍。** 可回滚单机进度走显式候选选择；高风险数据沿用可信协议。
6. **保全本地证据。** 不破坏唯一好档，创建/迁移与坏档恢复都有明确授权边界。
7. **修真实状态 UI。** 不只换一句“云档已同步”，确保每条异常路径有安全出口。
8. **回归、LSP、官方 build。** 不手写构建脚本、不手工改 dist。
9. **授权平台验收。** 登录、同账号刷新、切号、另一设备分别验证并记录。
10. **交付剩余缺口。** 不把没测的内容写成通过，也不把单局初始化误报为账号丢档。
