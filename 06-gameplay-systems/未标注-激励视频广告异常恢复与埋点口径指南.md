## 2. 先分清四种结果

| 类型 | 能证明什么 | 不能据此推断什么 |
|---|---|---|
| SDK 明确成功 | SDK 按当前契约报告本次成功 | 平台已记收益、已结算或提供了有效曝光 |
| 免费领取 | 业务允许玩家免费获得奖励 | 广告被请求、展示或完播 |
| 异常补偿 | 产品因未知结果或异常发放了体验补偿 | 原广告成功，或玩家已满足平台完播要求 |
| 平台收益数据 | 平台按其统计口径记录的收益或曝光 | 每个客户端事件都与平台记录一一对应 |

来源引用的 SDK 契约以 `result.success == true` 确认成功。焦点恢复、等待时间达到阈值、pending 存在或游戏恢复运行，都不能代替成功回调。

来源历史实现会在守卫或启动恢复中补奖，并推进部分广告相关计数。这是待区分的既有行为，不能作为“所有项目遇到超时都应算成功”的接入规范。

建议使用以下处理表；这属于改进目标，不表示来源已经实现：

| 结果 | 流程与奖励 | 统计类别 |
|---|---|---|
| SDK 成功 | 恢复流程，发正常奖励 | `sdk_success` |
| SDK 明确取消 | 恢复流程，不发正常广告奖励 | `user_cancel` |
| SDK 普通错误 | 恢复流程，不发正常广告奖励 | `sdk_error` |
| SDK 未受理 | 即时结束本次等待 | `request_rejected` |
| 无回调超时 | 解锁 UI，允许玩家稍后主动重试 | `callback_timeout` |
| 业务决定额外补偿 | 走独立补偿分支 | `compensation_granted` |
| 免费资格或测试降级 | 走明确的免费业务分支 | `free_granted` |

只有目标 SDK 能明确区分取消和错误时，才能分别记录；无法识别时保留未分类原因，不凭猜测归入取消。失败后不循环自动拉起广告，也不绕过平台防抖和冷却。

## 3. 沿完整链路检查，而非只检查播放调用

```text
玩家主动点击入口
  → 资格检查：是否已有请求、免费资格、GM 模式、业务次数限制
  → 记录入口与请求上下文
  → 如启用恢复机制，发起待处理记录写入
  → 调用 SDK，并处理同步受理结果
  → SDK 回调 / 焦点守卫 / 会话超时 / 下次启动恢复
  → 解除本次暂停与等待状态
  → 按结果发正常奖励、免费奖励或独立补偿
  → 保存业务状态，记录对应统计
```

逐入口建立清单：是否真正调用 SDK、是否增加次数、是否推进解锁进度、是否发奖励、是否消耗已存奖励、失败如何恢复。同一个“看广告”按钮可能走免费、测试或补偿路径，不能只从按钮名称判断结果。

来源中对应的职责包括：广告业务入口、每日共享池与充能、主循环恢复、待发奖励恢复、GM 统计入口、云端聚合。迁移时沿用目标项目结构，不为套用本案例另造同名模块。

## 4. 频控要分开业务资格与真实广告量

来源实现中，冲刺与投票共享每日免广告资格池；达到阈值后跳过 SDK，继续提供相应业务奖励。这样能减少重复观看，同时保留玩法功能，但不能仅凭阈值推导 eCPM 或总收益一定提高。

需要分别核对：

- 每日免广告阈值、奖励储存上限、单局复活上限、每日业务次数上限和皮肤累计进度；它们是不同限制。
- 频控计数在哪里判断、由谁写入、日期采用哪个时区。客户端判断、云端保存，不等于服务端权威频控。
- 免费、测试、补偿是否增加每日池或累计解锁。函数名带有“观看”并不保证只统计真实成功。
- 阈值效果需结合平台收入、玩家留存与真实观看分布评估，案例数字不作为通用经营结论。

来源的具体数值与各分支计数见第 10 节。

## 5. 防卡死：恢复流程独立于成功判定

### 5.1 正常回调

来源进入实际 SDK 分支时设置广告暂停、记录会话起点并暂停 BGM。回调无论成功还是失败，都先结束广告暂停和恢复音频，再处理奖励。

检查失败、取消、同步拒绝和未知结果是否也会解除本次输入锁、等待标记和音频暂停，不能把恢复操作仅放在成功分支。

来源两处 `ShowRewardVideoAd()` 调用未接收 boolean 返回值。材料引用的接口说明表示返回 `false` 时可能没有回调；目标项目确认具有这一契约后，应当场结束未受理请求，不能全部留给超时守卫。

### 5.2 焦点与超时守卫

来源监听 `InputFocus`，广告仍在等待时记录焦点恢复时刻；经过 `3.0` 的 `os.clock()` 差值后若仍未结束，执行守卫恢复。宽限是为了给迟到的 SDK 回调留时间。

另一条守卫在会话达到 `45` 的 `os.clock()` 差值时执行恢复。两者都依赖更新循环实际执行，不能写成“切后台后经过 45 秒墙钟时间必然恢复”。

来源守卫会补发奖励、清除 `adPaused` 及业务等待标记并恢复 BGM。迁移时保留防卡死能力，但是否补偿和如何计数必须单独定义，不能把未知结果自动标记为正常 SDK 成功。

### 5.3 防重复和点击穿透

来源广告等待期间拦截主要鼠标、触摸按下入口；确认弹窗关闭后保留约 `0.1` 的 `os.clock()` 差值保护，避免同次操作穿透。

守卫处理后清除 `adLoading`，迟到回调发现已不在等待时跳过发奖。这是按模块等待标记防重，不等于每个广告请求都有独立 ID，也不能据此断言已隔离所有跨请求迟到回包。

后续如增加 `request_id`，应让回调、守卫和恢复都关联同一请求，并核对旧请求回调能否影响已开始的新请求。这是建议，来源没有给出已验证实现。

## 6. 崩溃恢复：先发起写入的保障边界

来源在调用 SDK 前向 `ad_pending_reward` 发起云写入：

| 字段 | 来源用途 |
|---|---|
| `type` | 区分 `dash` / `vote` |
| `data` | 投票选项等业务数据 |
| `ts` | 记录时间戳 |
| `claimed` | 是否已经处理 |

正常结束或运行中补发后，以 `claimed = true` 覆盖记录。来源使用这一方式而非 `nil`，因为其云覆盖行为不能依靠省略 key 删除旧值；其他存储接口应按自己的删除与覆盖契约核对。

下次启动按下列顺序检查：

1. 已处理的记录不恢复。
2. 年龄小于 5 秒或大于 600 秒的记录丢弃。
3. 年龄在 5～600 秒的记录进入补发。
4. 设置本次启动的防重标记，先发起清除，再执行奖励。

来源没有等待云端确认写入后才调用广告，也没有等待清除确认后才发奖，因此只能称为尽力恢复。写入发起、持久化确认和领取结算不是同一件事；先清后发也不自动提供原子性。

记录年龄不能证明观看时长，pending 不能证明完播。来源对复活的守卫或启动补发仅补储存充能，不重建原死亡现场。

如需加强，来源建议引入独立请求 ID，分别记录请求、SDK 结果和领取状态，在适用的可信服务端做幂等领取，并分开正常奖励与异常补偿。以上尚未实现；不能宣称已经实现绝不丢奖或绝不重发。

## 7. 统计审查：先解释每个动作实际代表什么

来源未接入 `sdk:LogEvent` / TapDB 事件级链路，主要使用云端聚合计数：

| 业务入口 | 云端动作 | 来源含义 |
|---|---|---|
| `RecordRequest(source)` | `click` | 即将调用 SDK，不包含所有入口点击 |
| `RecordSuccess(source)` | `ok` | SDK 成功回调 |
| `RecordFail(source)` | `skip` | 取消和普通错误等非成功结果混合 |
| `RecordSkip()` | `free` | 免费、无 SDK、不支持平台等降级 |
| `RecordRescue(source)` | `rescue` | 守卫或启动补发 |

### 7.1 漏斗和维度缺口

- 开发者免费、每日免费、无 SDK 等路径通常没有 `click`，所以它不能代替入口点击量。
- `skip` 不是纯主动关闭，不能把该计数直接解释为玩家观看意愿。
- `dash` / `vote` 来源参数仅用于日志，没有进入云端维度，无法按入口拆分报表。
- `unsupported platform` 可能同时产生 `click + free`，请求和免费不是互斥分类。

### 7.2 存储和查询边界

生涯字段为 `adm_click`、`adm_ok`、`adm_free`、`adm_skip`、`adm_rescue`；另有动作总数 `adm_total` 及周几桶 `adm_w1`～`adm_w7`。

| 现象 | 正确解释 |
|---|---|
| 一次请求和一次成功各记一次 | `adm_total` 是动作次数和，不是播放次数 |
| 周几桶每维 6 bit | 只能表示 0～63，超过会回绕 |
| 只有星期几，没有完整日期或周号 | 不能直接解释为最近七个自然日 |
| 面板固定查询前 50 条 | 汇总仅代表返回样本，不是全服总量 |

### 7.3 成功率公式不能脱离计数定义

来源面板采用：

```text
(ok - rescue) / (click - skip)
```

但补发只增加 `rescue`，没有同步增加 `ok`，再从 `ok` 减去补发会错配；`skip` 又混有普通错误，不能全部当作主动放弃扣除。

因此该面板值不能直接当成 SDK 成功率、完播率或填充率。复用旧监控方案前，先按真实分支核对分子和分母，不能只复制公式和健康阈值。

## 8. 开发者、应用和 GM 身份各管什么

| 身份或维度 | 用途 | 边界 |
|---|---|---|
| `developer_id` | 厂商归属、厂商层汇总与对账 | 不是密码或 GM 权限凭证 |
| `app_id` | 区分具体游戏应用 | 同厂商不同游戏不能只按厂商 ID 混算 |
| 玩家 UID | 玩家数据、排障与账号角色 | 不应拿它与厂商 ID 比较 |
| `is_gm` | 区分开发者行为 | 技术排障可保留，正式运营报表应能筛除 |
| `environment` | 区分正式、预览、测试 | 免费模拟不冒充生产广告流量 |

来源使用 `clientCloud.userId` 与脚本中的玩家 UID 白名单比较，开启 `DEV_MODE`。客户端功能门控不等于服务端安全授权。

来源 GM 三态开关的含义：

| 状态 | 来源行为 |
|---|---|
| `nil` 正常 | 按每日池判断；开发者冲刺仍有默认免费特权 |
| `false` 关闭免广告特权 | 绕过每日免费资格，进入实际 SDK 尝试路径 |
| `true` 开启免广告特权 | 冲刺和投票走免费路径 |

该开关不是广告总开关，进入 SDK 路径不保证有广告可展示。来源开发者行为仍混入同一套统计，也没有输入任意玩家 UID 后远程修改其广告参数的功能。

后续增加身份维度时，从可信项目或平台上下文关联 `developer_id` / `app_id`，不允许玩家覆盖，不上传凭据；宿主已有的公共属性不重复报送。

## 9. 事件级埋点与指标建议（来源尚未实现）

### 9.1 事件

| 事件 | 含义 |
|---|---|
| `ad_entry_click` | 玩家点击业务入口 |
| `ad_request` | 调用 SDK |
| `ad_request_rejected` | SDK 同步未受理 |
| `ad_sdk_result` | SDK 成功、取消或错误 |
| `ad_callback_timeout` | 等待后未得到有效回调 |
| `ad_reward_granted` | 正常广告奖励已发放 |
| `ad_free_granted` | 免费资格或测试降级奖励已发放 |
| `ad_compensation_granted` | 独立异常补偿已发放 |
| `ad_recovery_result` | 启动恢复的结果 |

若公开 API 没有真实曝光或播放开始回调，不虚构 `ad_impression` 或“开始播放”事件。

建议公共字段为 `request_id`、`entry`、`app_version`、`environment`、`is_gm`、`accepted`、`result_type`、`error_reason`、`elapsed_ms`、`reward_type`、`reward_amount`、`daily_count`。入口可区分预存、复活和投票；耗时表示调用到结果的间隔，不冒充真实广告播放时长。

材料引用的 `sdk:LogEvent` 成功语义是本地持久化成功，不保证服务端已收到；实施前核对目标版本，并独立处理业务去重。

### 9.2 报表

| 指标 | 建议口径 |
|---|---|
| 请求受理率 | SDK 受理请求数 / SDK 调用数 |
| SDK 成功回调率 | SDK 成功回调数 / 受理请求数 |
| 回调超时率 | 超时请求数 / 受理请求数 |
| 已知结果取消占比 | 明确主动关闭数 / 已知结果数 |
| 正常奖励发放率 | 正常奖励已发放数 / SDK 成功数 |
| 补偿率 | 异常补偿数 / 广告请求数 |
| 免费比例 | 免费领取数 / 全部相关奖励领取数 |

按请求 ID 去重并采用相同时间范围、入口与环境过滤条件；分母为零时显示无样本。对于尚未获得受理结果的请求，保留未知状态，不默认为受理成功。

收入、有效曝光、填充率和 eCPM 使用平台实际提供的口径，客户端回调与这些数据分开呈现。

## 10. 来源案例：具体参数、奖励和计数分支

本节仅保存《唐三藏：踩云之上》材料描述的配置，供理解和回溯；不作为其他项目的默认值。

### 10.1 参数

| 项目 | 来源记录 |
|---|---|
| 广告总开关 | `ADS_ENABLED = true` |
| 每日共享免广告阈值 | 10 次，冲刺和投票共享 |
| 广告充能储存上限 | 20 次，与每日阈值不同 |
| 普通冲刺 | 无单局次数上限，但消耗充能 |
| 复活 | 每局最多 3 次，仅消耗广告充能 |
| 投票 | 每日最多 10 票 |
| 七彩祥云 | 累计广告进度 20 次解锁 |
| 焦点宽限 | `os.clock()` 差值 3.0 |
| 会话超时 | `os.clock()` 差值 45 |
| 弹窗点击保护 | 约 0.1 的 `os.clock()` 差值 |
| 启动恢复窗口 | pending 年龄 5～600 秒 |

来源明确说明历史概念中的“每日真实 20 次、免费 80 次”不是该代码记录的参数。

### 10.2 三个实际入口

| 入口 | 来源记录的奖励与行为 |
|---|---|
| 准备界面预存冲刺 | 正常成功后：充能 +1、功德 +1、共享每日池 +1、七彩祥云进度 +1；只储存，不立即冲刺 |
| 下落时复活 | 有充能则直接消耗复活，不播广告；没有充能才进入广告流程；正常成功后获得充能并立即消耗，增加本局复活次数并冲刺 |
| 更新投票 | 正常成功后：所选方案 +1 票、充能 +2、功德 +1、共享每日池 +1、七彩祥云进度 +1 |

免费投票也送 +2 充能，但没有功德和广告累计进度；来源旧注释“免费仅计票、不送充能”与实际执行不一致。

七彩祥云皮肤格已不是独立广告入口，而是通过其他入口累积进度。复活的守卫或启动补发仅补存储充能，不自动恢复死亡现场。

### 10.3 每日池与累计皮肤进度

来源 `RecordAdWatch(isReal)` 无论参数真假都会增加每日计数，只有 `isReal=true` 才推进皮肤累计进度。各业务分支实际调用不同：

| 分支 | 增加共享每日计数 | 推进皮肤进度 |
|---|---|---|
| SDK 正常成功 | 是 | 是 |
| 冲刺免费领取 | 是 | 否 |
| 免费投票 | 否 | 否 |
| AdGuard 补发 | 是 | 是 |
| 启动补发 | 是 | 是 |
| 无 SDK 的投票降级 | 是 | 是 |

因此今日计数、皮肤进度和真实完播次数不能互相替代。每日池由客户端判断、云端保存，日期使用 `os.date()`，不能据此宣称具有平台统一时区或服务端权威限额。

## 11. “广告出不来”的定位顺序

| 顺序 | 核对项 |
|---|---|
| 1. 入口 | 是否进入真实业务函数；来源日志例为 `WatchAd called` / `Vote.CastVote called` |
| 2. 资格 | 是否已有 `adLoading`、业务次数用尽或已进入免费分支 |
| 3. 开发者模式 | GM 默认免广告是否导致根本没有调用 SDK |
| 4. SDK 存在性 | 当前平台是否存在 SDK 和相应方法 |
| 5. 请求受理 | 检查同步返回值，是否未受理且可能没有回调；来源尚未记录此层 |
| 6. SDK 结果 | 保存实际 `success`、`msg`，区分已知错误和未知结果 |
| 7. 无回调 | 是否进入焦点宽限或超时守卫，是否恢复等待状态和音频 |
| 8. 奖励 | 是正常奖励、免费领取还是补偿，存档是否成功 |
| 9. 平台配置 | 如本次任务已授权，重新同步官方配置，检查真实状态与提示 |

来源的 `[AD-DIAG]` 可辅助逐层定位。本地 `status=1` 只是上次保存的状态，不保证此刻每次都有广告展示；失败后不通过循环重试绕过平台策略。
