# 规格与需求卡

## 1. 事实源与适用范围

核对日期：**2026-10-31（Asia/Shanghai）**。规格是查询快照，不是永久规则。

- TapTap 小游戏专项：[宣发物料指引](https://developer.taptap.cn/minigameapidoc/quick-start/guide/game-publish/material/)。
- TapTap 通用商店：[游戏物料要求 v4](https://developer.taptap.cn/docs/store/release/publish/material/)。
- Maker 官网：[TapTap 制造](https://maker.taptap.cn)。官网生成能力与“TapTap 开发者中心发布字段”是两件事。
- 实际发布页：核对具体游戏、系统、预约/下载/试玩阶段和字段校验。若页面与专项文档冲突，保留冲突并核实，不把某项更宽松的限制套到另一个渠道。

本次检索发现旧项目记录里的“截图最多 5 张”“所有视频 1–10 分钟、500MB”“所有图片一律 2MB”等不能作为通用商店现行规则。小游戏和通用商店的尺寸、体积、视频要求分别记录；不要混抄。

## 2. 小游戏专项快照

| 项目 | 查询到的要求 | 制作建议（不是额外平台强制要求） |
|---|---|---|
| 简介 | 提供游戏简介 | 先讲玩家做什么，再讲特色 |
| 横宣传图 | 1920×1080，JPG/PNG，2MB 内，1 张；有名称/Logo，无其他文字 | 横方共用同一主视觉 |
| 方宣传图 | 1440×1440，JPG/PNG，2MB 内，1 张；同上文字限制 | 重新构图，不裁掉人物/游戏名 |
| 实机截图 | 不低于 1280×720，单张 2MB 内，至少 3 张，JPG/PNG | 随游戏方向准备，竖版基线可取 720×1280；再查实际字段 |
| 实机录屏 | 横版 16:9 ≥1280×720；竖版 9:16 ≥720×1280；500MB 内，1 条 MP4，H.264/HEVC | 优先真实核心玩法，常见交付可选 1080p |
| 首页推荐素材 | 按目标后台配置推荐素材 | 回填是独立写入动作，先确认授权 |

专项表没有列出的数量上限、视频时长等，不从旧记录补成规定；再查当期发布页与适用的通用要求。

## 3. 通用商店 v4 快照

| 项目 | 查询到的要求 |
|---|---|
| 游戏 Icon | 1:1，至少 512×512，PNG/JPG；直角方图，不自行裁圆角；非默认图，不用纯白/纯黑/透明底 |
| 游戏 Logo（电脑/主机等对应字段） | PNG，宽达到 1280 或高达到 720 即可，自定义比例，4MB 内；设计外区域透明 |
| 横版游戏封面 | 460×215，PNG/JPG，3MB 内；有游戏名/Logo，无额外宣传文字 |
| 竖版游戏封面 | 600×900，PNG/JPG，3MB 内；同上 |
| 游戏库壁纸 | 3840×1240，PNG/JPG，10MB 内；无文字/Logo，避开系统 UI 与叠加 Logo |
| Windows 无 Logo 宣传图 | 横 ≥1920×1080，竖 ≥720×1080，各 1 张，相同或相似主体，PNG/JPG，各 6MB 内；无任何文字/Logo |
| 横版宣传图 | ≥1920×1080，16:9，PNG/JPG，4MB 内；必须游戏名，不要其他文字、Icon、直接截图或简单拼贴；兼顾 4:3 裁切 |
| 方形宣传图 | ≥1440×1440，1:1，PNG/JPG，4MB 内；与横版同主体，允许为版式调整人物/Logo；上传竖版实机视频时需要 |
| 实机截图 | 横 ≥1280×720，比例 8:3～8:5；竖 ≥720×1280，比例 3:8～5:8；同向同宽高比，至少 3 张，不重复，PNG/JPG，每张 ≤4MB，建议 ≤1MB |
| 实机视频 | MP4/MOV，H.264/HEVC，≤5GB；时长 >15秒、≤30分钟，建议 2 分钟内；短边 ≥540，比例 21:9～9:21 |
| 宣传片 | 仅 16:9 横屏，≥1280×720，建议 1920×1080；MP4/MOV，H.264/HEVC，≤5GB，至少 15秒 |
| 编辑推荐图 | 仅适用于编辑推荐游戏：1920×1280，3:2；提供 PNG/JPG，建议附真正可编辑 PSD；走对应工单，不擅自给未获资格游戏提交 |

注意：512 Icon 的体积上限在本次通用文档对应段没有写出，按实际字段核对；不要凭过去项目写死 2MB。2MB 可作跨小游戏与通用商店的保守图片目标，但不是所有字段的官方统一限值。

## 4. 截图与实机的内容规则

通用截图：真实实机画面至少占图片的 50%；概念/广告类图片至多 2 张，实机截图排在最前。不能添加不存在的玩法、伪造操作界面或过度美化实际游戏；不能只给卡片、立绘、Loading、主菜单或充值/抽卡画面。

通用实机视频：前 5 秒进入核心玩法，并连续展示核心玩法超过 10 秒；前 30 秒纯展示、CG、立绘、抽卡/过场动画合计不得超过 10 秒。不得外加游戏本体之外的配音/字幕、前贴片、画中画、实物手机或导流水印；录屏内容占比须在 80% 以上。允许适当加速、减速、拼接，但应诚实说明剪辑性质，不伪装连续原速录屏。

实际项目可采用“前 3 秒入玩法、60–120 秒演示”等更严格制作目标；这是体验策略/用户需求，不是把官方前 5 秒规则改写了。

## 5. 通用需求卡

用已有信息填，不把每个空项变成问卷：

```yaml
game:
  title: 游戏全名
  genre: 游戏类型与玩家动作
  platform: H5 / Android / iOS / PC / 其他
  orientation: portrait / landscape
  release_stage: reservation / playable / download
  core_loop: 输入动作 -> 反馈 -> 结果 -> 下一次动机
  real_features: [已实现特色一, 已实现特色二, 已实现特色三]
  art_anchor: 现有美术与参考文件
  forbidden_inventions: [不存在的玩法, 未实装角色, 虚假奖励]
assets_requested:
  required: [当前渠道实际必填项]
  optional: [宣传片, BGM, 配音, 3D 等确实需要的项]
  actual_field_specs: 每个字段的尺寸/格式/体积/时长及来源日期
maker:
  channel: mcp / website
  verified_account: 已确认账号，不填凭证
  project: 实际接收项目，不照抄示例项目
  target_dir: MCP 时填写唯一绝对项目根
  budget: 用户已批准的普通额度与额外确认门槛
stop_at: candidate_delivery / draft_upload / review_check / explicit_submission
```

完整套餐按适用范围覆盖：Icon、标题/Logo、横方主视觉、截图组、实机演示、宣传片、视频封面、简介/开发者的话/更新日志。音乐、音效、配音、动效和 3D 仅在内容需要时加入；电脑/主机字段和编辑推荐图也不是所有手机游戏必做项。
