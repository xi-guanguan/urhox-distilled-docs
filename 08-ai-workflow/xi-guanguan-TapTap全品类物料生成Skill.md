## TapTap 全品类物料生成

把游戏的真实卖点、已有资产和发布字段转成一套视觉统一、来源可追、可实际上传的物料。适用于 2D/3D、横版/竖版、休闲/动作/叙事/经营等游戏，不绑定某款游戏、某种美术或某个运行引擎。

### 生成渠道与边界

- **所有新增创意资产只由 Maker MCP 或 Maker 官网生成/修改。** 包括图片、生成视频、音乐、音效、角色声音和可选 3D。文案如需标注“由 Maker 生成”，也须在官网写作入口实际生成；MCP 没有普通文案工具时不要冒造工具。
- 不切到其他生图/视频供应商，不拿 HTML/CSS/Canvas/SVG、OpenFilm、Remotion 或素材拼贴冒充 Maker 生成。可在本地做读取、质量检查、哈希、压缩、格式转换等技术处理；本地创意排版、混剪或重新绘制不在默认范围，需要另行获得用户许可并标清来源。
- 真实游戏截图/录屏、已有 Logo 和美术是**真实性底稿**，不是允许 AI 虚构的内容。生成画面不能代替“实机截图/实机录屏”；缺少真实底稿时可继续制作其他资产，但该项必须如实列缺口。
- Maker 只是素材供应商时，不改变游戏引擎或平台，不自动 init、迁移、上传源码、构建、提交或发布。
- 当前工具 schema、实际发布页和官方专项文档高于本文快照。官网按钮、可用模型、价格、时长与能力运行时核对，不凭旧经验补造入口。

不要为了做一张图读完所有分支；用户明确要整套时覆盖所有适用项，不把可选 3D、配音等变成强制消费。

### 主流程

#### 1. 确定物料合同

从已有游戏和目标字段提取：游戏名、平台、方向、美术锚点、核心循环、三项真实卖点、现有截图/录屏、需要的物料、预算、截止时间与停点。优先自己查文件与页面，只问无法推断的关键决定。

默认停点为**生成、验收并交付候选文件**。上架回填、上传 GitHub、提审和正式发布分别按本次授权执行，不从历史对话继承批准。

#### 2. 锁定身份、项目与参考

MCP 先读 `maker://status`，不可用时用 `maker_status_lite`。核对当前账号与接收项目；已确认的身份沿用，只有歧义/冲突/要求切换时再确认。每次素材调用显式传唯一 Maker 项目根 `target_dir`，把参考路径与投递根分开记录。新建、恢复绑定、换账号均不是制作 Skill 的隐含授权。

官网路径核对登录账号、项目名/ID、素材保存位置；切换到官网不代表允许换账号或借其他游戏扣积分。没有可用接收项目时，继续需求和提示词准备，不擅自初始化。

#### 3. 先形成一套视觉，再扩展尺寸

复用现有资产与历史合格主视觉；参考图分别注明“身份/美术/构图/结构”的职责。先做一个母版，检查人物身份、光线、空间关系和游戏关联，再用 `edit_image` 扩展横版、方版及其他版式。独立资产可以批量，依赖上一版结果的衍生图不能提前并发。

图片和视频的提示词写明：用途、参考职责、主体、画风、构图、留白、允许变化、禁止变化与尺寸。不要把“高级、好看、爆款”当作规格。

#### 4. 生成与必要审核

使用当前真实存在的 MCP 工具或官网入口。普通图片默认 `model="default"`，用户明确指定后端才换。视频仅在明确要求视频时生成，先按当前规则估算积分；超过工具要求的再次确认门槛时必须等本人明确确认。声音候选和 3D 审核图均展示后等本人选择，不自动批准。

异步任务按 task/asset ID 查询；超时不等于失败，不盲目重复消费。使用返回的本地路径和远端映射，不猜文件名；部分成功就保留成功项，仅处理失败项。

#### 5. 验收与交付

同时验三层：
1. **技术**：尺寸、比例、格式、体积、时长、解码、音轨、字幕、裁切与最终文件哈希。
2. **内容**：统一美术、非素材堆叠、文字正确、玩法真实、截图未被 AI 改写、视频不变脸/变物体，音乐首尾自然。
3. **渠道**：逐项对应实际发布字段，真实截图与概念图不混位，宣传片与实机不混标；如获准回填，保存后回读缩略图、顺序、视频字段及包体。

报告实际完成项、来源、费用中已知/未知部分、尚缺项及停点。文件合规不等于审核通过，生成成功不等于已接入成片，上传成功不等于已提审或已发布。

### 官网直接学习

用户只有 Maker 官网时，可阅读同目录参考材料，或使用配套完整蒸馏文档的一条链接。让官网助手先读规则、识别其实际能力、列缺口，再实际生成；不能访问 GitHub 时上传 Markdown 或粘贴全文，不假称读过。

## 规格与需求卡

### 1. 事实源与适用范围

核对日期：**2026-10-31（Asia/Shanghai）**。规格是查询快照，不是永久规则。

- TapTap 小游戏专项：[宣发物料指引](https://developer.taptap.cn/minigameapidoc/quick-start/guide/game-publish/material/)。
- TapTap 通用商店：[游戏物料要求 v4](https://developer.taptap.cn/docs/store/release/publish/material/)。
- Maker 官网：[TapTap 制造](https://maker.taptap.cn)。官网生成能力与“TapTap 开发者中心发布字段”是两件事。
- 实际发布页：核对具体游戏、系统、预约/下载/试玩阶段和字段校验。若页面与专项文档冲突，保留冲突并核实，不把某项更宽松的限制套到另一个渠道。

本次检索发现旧项目记录里的“截图最多 5 张”“所有视频 1–10 分钟、500MB”“所有图片一律 2MB”等不能作为通用商店现行规则。小游戏和通用商店的尺寸、体积、视频要求分别记录；不要混抄。

### 2. 小游戏专项快照

| 项目 | 查询到的要求 | 制作建议（不是额外平台强制要求） |
|---|---|---|
| 简介 | 提供游戏简介 | 先讲玩家做什么，再讲特色 |
| 横宣传图 | 1920×1080，JPG/PNG，2MB 内，1 张；有名称/Logo，无其他文字 | 横方共用同一主视觉 |
| 方宣传图 | 1440×1440，JPG/PNG，2MB 内，1 张；同上文字限制 | 重新构图，不裁掉人物/游戏名 |
| 实机截图 | 不低于 1280×720，单张 2MB 内，至少 3 张，JPG/PNG | 随游戏方向准备，竖版基线可取 720×1280；再查实际字段 |
| 实机录屏 | 横版 16:9 ≥1280×720；竖版 9:16 ≥720×1280；500MB 内，1 条 MP4，H.264/HEVC | 优先真实核心玩法，常见交付可选 1080p |
| 首页推荐素材 | 按目标后台配置推荐素材 | 回填是独立写入动作，先确认授权 |

专项表没有列出的数量上限、视频时长等，不从旧记录补成规定；再查当期发布页与适用的通用要求。

### 3. 通用商店 v4 快照

| 项目 | 查询到的要求 |
|---|---|
| 游戏 Icon | 1:1，至少 512×512，PNG/JPG；直角方图，不自行裁圆角；非默认图，不用纯白/纯黑/透明底 |
| 游戏 Logo（电脑/主机等对应字段） | PNG，宽达到 1280 或高达到 720 即可，自定义比例，4MB 内；设计外区域透明 |
| 横版游戏封面 | 460×215，PNG/JPG，3MB 内；有游戏名/Logo，无额外宣传文字 |
| 竖版游戏封面 | 600×900，PNG/JPG，3MB 内；同上 |
| 游戏库壁纸 | 3840×1240，PNG/JPG，10MB 内；无文字/Logo，避开系统 UI 与叠加 Logo |
| Windows 无 Logo 宣传图 | 横 ≥1920×1080，竖 ≥720×1080，各 1 张，相同或相似主体，PNG/JPG，各 6MB 内；无任何文字/Logo |
| 横版宣传图 | ≥1920×1080，16:9，PNG/JPG，4MB 内；必须游戏名，不要其他文字、Icon、直接截图或简单拼贴；兼顾 4:3 裁切 |
| 方形宣传图 | ≥1440×1440，1:1，PNG/JPG，4MB 内；与横版同主体，允许为版式调整人物/Logo；上传竖版实机视频时需要 |
| 实机截图 | 横 ≥1280×720，比例 8:3～8:5；竖 ≥720×1280，比例 3:8～5:8；同向同宽高比，至少 3 张，不重复，PNG/JPG，每张 ≤4MB，建议 ≤1MB |
| 实机视频 | MP4/MOV，H.264/HEVC，≤5GB；时长 >15秒、≤30分钟，建议 2 分钟内；短边 ≥540，比例 21:9～9:21 |
| 宣传片 | 仅 16:9 横屏，≥1280×720，建议 1920×1080；MP4/MOV，H.264/HEVC，≤5GB，至少 15秒 |
| 编辑推荐图 | 仅适用于编辑推荐游戏：1920×1280，3:2；提供 PNG/JPG，建议附真正可编辑 PSD；走对应工单，不擅自给未获资格游戏提交 |

注意：512 Icon 的体积上限在本次通用文档对应段没有写出，按实际字段核对；不要凭过去项目写死 2MB。2MB 可作跨小游戏与通用商店的保守图片目标，但不是所有字段的官方统一限值。

### 4. 截图与实机的内容规则

通用截图：真实实机画面至少占图片的 50%；概念/广告类图片至多 2 张，实机截图排在最前。不能添加不存在的玩法、伪造操作界面或过度美化实际游戏；不能只给卡片、立绘、Loading、主菜单或充值/抽卡画面。

通用实机视频：前 5 秒进入核心玩法，并连续展示核心玩法超过 10 秒；前 30 秒纯展示、CG、立绘、抽卡/过场动画合计不得超过 10 秒。不得外加游戏本体之外的配音/字幕、前贴片、画中画、实物手机或导流水印；录屏内容占比须在 80% 以上。允许适当加速、减速、拼接，但应诚实说明剪辑性质，不伪装连续原速录屏。

实际项目可采用“前 3 秒入玩法、60–120 秒演示”等更严格制作目标；这是体验策略/用户需求，不是把官方前 5 秒规则改写了。

### 5. 通用需求卡

用已有信息填，不把每个空项变成问卷：

```yaml
game:
  title: 游戏全名
  genre: 游戏类型与玩家动作
  platform: H5 / Android / iOS / PC / 其他
  orientation: portrait / landscape
  release_stage: reservation / playable / download
  core_loop: 输入动作 -> 反馈 -> 结果 -> 下一次动机
  real_features: [已实现特色一, 已实现特色二, 已实现特色三]
  art_anchor: 现有美术与参考文件
  forbidden_inventions: [不存在的玩法, 未实装角色, 虚假奖励]
assets_requested:
  required: [当前渠道实际必填项]
  optional: [宣传片, BGM, 配音, 3D 等确实需要的项]
  actual_field_specs: 每个字段的尺寸/格式/体积/时长及来源日期
maker:
  channel: mcp / website
  verified_account: 已确认账号，不填凭证
  project: 实际接收项目，不照抄示例项目
  target_dir: MCP 时填写唯一绝对项目根
  budget: 用户已批准的普通额度与额外确认门槛
stop_at: candidate_delivery / draft_upload / review_check / explicit_submission
```

完整套餐按适用范围覆盖：Icon、标题/Logo、横方主视觉、截图组、实机演示、宣传片、视频封面、简介/开发者的话/更新日志。音乐、音效、配音、动效和 3D 仅在内容需要时加入；电脑/主机字段和编辑推荐图也不是所有手机游戏必做项。

## 图片与文案

### 1. 先整理品牌参考，不从杂乱素材开始拼贴

只读与本次物料有关的资产。建立一页小型视觉约束：主色/辅色、线条、材质、视角、光源、人物身份特征、文字风格、Logo 与留白区。标清参考职责：

- 身份参考：脸、发型、服饰、道具不可随意变化。
- 画风参考：线条、色彩、材质和细节密度，不代表照抄构图。
- 结构参考：建筑/武器/车辆/棋盘等的形状，避免生成器“合理化”成另一件物品。
- 构图参考：可借层次和重心，不复制他作品牌、角色、标题或水印。

已有一系列合格宣传图时先复用，不重做成“把素材摆满画布”。图里的物体需要共享空间、透视、光源与叙事关系。

### 2. 覆盖矩阵与制作顺序

| 类别 | 核心验收 | Maker 路径 |
|---|---|---|
| Icon | 小尺寸一眼可辨、视觉焦点少、与游戏一致；商店 Icon 不交透明底 | 单图生成，选定后 edit 迭代 |
| Logo/标题字 | 名称逐字正确，轮廓可读，背景透明需求与 Icon 区分 | Maker 生图/编辑，必要时传已有 Logo 作为参考；不要靠错误字硬交付 |
| 横主视觉 | 一件具体、有游戏关系的事；前中后景和自然留白；仅游戏名 | 先母版，再 Logo/标题编辑版 |
| 方主视觉 | 同一场景/人物/色调，重新安排主体与文字，不粗暴裁切 | 对已验收母版 `edit_image` |
| 商店截图组 | 各讲一个已实现卖点，真实 UI 清楚、同尺寸同向，优先展示玩法 | 真实截图输入；Maker 背景模板/官网排版或可验证保真编辑 |
| 视频封面 | 对应真实成片内容；遵守横/方宣传图字段要求 | 复用合格主视觉的适配版 |
| 活动图/社媒图/横竖海报 | 针对各自渠道的文字、尺寸和行动指引，不套商店禁止额外文字的图 | 从品牌母版衍生，各渠道单独验收 |
| 可选角色、道具、场景、序列帧底稿 | 服务物料或游戏内容，不能顺带扩大为全套游戏资产重做 | 对应图片/3D 流程；动图/帧图能力实际核对 |

### 3. 通用主视觉提示词

```text
为《[游戏名]》制作[渠道/用途]主视觉，尺寸[宽×高]，比例[比例]。
参考图1只用于[角色身份]；图2用于[画风与配色]；图3用于[场景结构]。
具体画面：[主角]正在[与游戏真实体验对应的一个动作/情境]。
画面有[前景]、[中景主体]、[远景]，统一[光源方向、材质、视角]。
构图重心在[位置]，[区域]自然留白用于游戏名，非白洞或空矩形。
必须保留：[人物身份、关键道具、视觉锚点]。
仅允许变化：[镜头、姿态、环境气氛等]。
禁止：[额外人物、错误肢体、现代物件、假UI、水印、二维码、素材相册式拼贴]。
[无字底稿：不要任何文字；或最终版：仅精确写“游戏全名”，无其他文字]。
```

无字母版只是中间件；最终字段要求游戏名时，必须经 Maker 编辑/官网可用排版实际完成文字。不会排对中文字时，提供正确 Logo 参考继续编辑；不能把“后期可加字”当作已完成。

方版编辑示例：

```text
把这张已验收主视觉重构为[1:1，1440×1440]，不是简单裁切。
人物身份、关键道具、光源、画风和场景关系保持一致。
将[主体]移到[位置]，完整保留脸和手；[区域]自然留出游戏名空间。
只调整构图与必要背景延展，不增加功能、角色或文字，不做拼贴。
```

可跨类型替换：动作游戏讲一次可实现的闪避/对抗；赛车讲真实车辆与赛道；解谜讲谜题主题但不假造解法 UI；经营讲玩家经营结果；叙事讲已存在的人物关系。不要把“国风、暖色、蒸笼、合成棋盘”固化成通用默认。

### 4. 真实截图包装：不能让 AI 重画游戏

保留三份并分清文件名：`raw_capture` 真实底稿、`maker_template` 生成背景、`store_final` 最终候选。上传清单只能指向验收过的 `store_final`，避免把原始截图当成包装版提交。

工作步骤：
1. 选择三个不同且已实现的核心场景：主玩法、成长/关卡结果、另一项特色；不要用主菜单/商城凑数。
2. 先核对字段允许的包装程度。通用商店至少 50% 真实画面；小游戏更严格字段则跟随其规则。大标题、装饰背景不是所有截图字段都可以用。
3. Maker 生成与品牌统一的背景模板，说明“不要生成棋盘、界面、按钮或文字；为真实截图留连续干净区域”。
4. 仅当官网实际支持保真图层/排版，才锁定真实截图层完成包装；或以 `edit_image` 尝试背景编辑，明确保护 UI。但**提示词承诺保真不等于像素保真**。
5. 对照原图检查所有数值、格子、道具、文字、手指、菜单边界；如可获取底层图则比较受保护区域像素。AI 改了 UI 的结果淘汰，不能称实机截图。
6. Maker 当前无法保真合成时，交付“真实截图 + Maker 模板 + 未完成原因”，不要自行换成本地 Canvas 拼接。用户另行允许本地精确合成后才做，并明示它是合成技术处理，不是 Maker 一步生成。

若允许标题，每张只讲一个真实卖点，标题与截图互相证明，不写“无限资源、全自动、零等待”等未实现承诺。不要假手机壳，不遮挡关键 UI，不把游戏变成另一种视觉密度。

### 5. 文案全套

| 文案 | 应写内容 | 不该混入 |
|---|---|---|
| 一句话介绍/短卖点 | 玩家动作 + 目标/情绪，一眼知道是什么 | 空泛的“全新沉浸、无限可能” |
| 游戏简介 | 类型、核心循环、可验证的特色；重点放前面 | 未实装功能、联系方式、群号、兑换码、受限外链 |
| 开发者的话 | 真实设计动机与具体小事，有个人语气 | 复制简介、虚构开发经历、模板式卖惨/免责 |
| 更新日志 | 本次版本实际变化，有序简短 | 广告、宣传口号、与版本无关内容 |
| 截图标题/视频旁白/字幕 | 与对应画面一致，少而可读 | 商店主视觉禁用的额外文案、实机字段禁用的新增字幕/配音 |
| 社媒发布文案 | 按发布渠道和受众写 | 把社媒导流话术直接塞进商店字段 |

官网写作提示词：

```text
根据本项目已实现功能，生成[一句话介绍、简介、开发者的话、更新日志]。
核心循环：[动作->反馈->结果]；真实特色：[列表]；玩家受众：[受众]。
口吻：[适合本游戏的具体口吻]，简短自然，用具体动作和小事，不做防御性说明。
简介与开发者的话不要雷同；主要信息优先放前50字。
不虚构经历、不承诺未实现功能、不加联系方式、群号、兑换码或受限链接。
额外风格要求：[例如不使用emoji/短小红书口吻，按本次用户要求填写，不跨游戏强制继承]。
先指出事实不足，不用编造补齐。
```

只写文案不自动改后台。MCP 没有通用文本工具时，最终 Maker 文案走官网；Codex 可做事实清单、检查和提示词准备，但不能把自己写的稿子标成官网生成。

## 视频与音频

### 1. 两条视频是两类交付

| 维度 | 实机/玩法演示 | 宣传片 |
|---|---|---|
| 证据来源 | 游戏真实运行画面；人工或明确获准的引擎驱动采集 | 可结合真实玩法与 Maker 生成的品牌/气氛镜头 |
| 核心目标 | 让玩家看懂操作、反馈、结果与成长 | 形成印象、节奏、情绪与吸引力，但不能虚构可玩内容 |
| 允许的生成画面 | 不能替代实机证据 | 可作氛围/故事/转场，清楚区分 CG 与玩法 |
| 时长 | 按渠道和用户需求；示例 60–120秒，不把十几秒样段当用户要求的一分钟 | 按渠道和用户需求；示例 30–90秒，长片逐镜生成 |
| 文字声音 | 按实机字段规则，不外加游戏本体外字幕/配音 | 按宣传片字段可用旁白/字幕，但不遮挡真实玩法 |
| 交付命名 | `gameplay-recording` / `gameplay-edited` / `engine-driven-demo` | `promotion` / `concept-pv` 等真实类型 |

引擎驱动、人工设置初始进度的演示不等于自然成长、手机录屏或真人体验；程序模拟重画的假 UI 更不能叫实机。素材任务不隐含允许浏览器代玩、修改玩家档、写测试作弊功能或 Maker 构建。

**Maker-only 的能力边界**：Maker 可以生成宣传镜头，但不能凭空生成真实录屏。没有真实录屏时先交其余物料并说明缺口；可让用户提供实际采集，或在另行授权下采集。官网若没有拼接/混音能力，就交镜头包，不假称已经完成长片，也不自动改用 OpenFilm/ffmpeg 做创意剪辑。

### 2. 实机演示节奏

先有一个连续的核心动作段，避免从启动、菜单、漫长生产等待开始。节奏围绕“动作—结果—新目标”，不是围绕静态功能列表。

- 合成/经营：连续合成/交单/建设结果形成正反馈；别只反复点生成器。
- 动作/射击：移动、识别威胁、攻击/闪避、命中反馈、局面变化；别用一分钟站桩代替玩法。
- 赛车：入弯、超车/避障、速度反馈、比赛结果；不生成游戏里做不出的漂移。
- 解谜/叙事：给出一个可理解的局部推理/选择与结果，适量避剧透。

可以选用隔离演示前态，但不要显示开发按钮、无限资源界面或假装自然进度。加速/跳切按渠道允许范围和实际事实标记；若纯实机字段不允许新增文字，把倍率说明放文件说明/物料页，不在画面里强加字幕。原速动作段保留足够长，避免让玩家误判游戏节奏。

### 3. 宣传片分镜与短镜头生成

先写镜头表，再花积分。示例结构仅作策略：开头直接看核心动作 -> 展示一项结果 -> 少量风格镜头 -> 第二项真实特色 -> 品牌收尾。开头长 Logo、PPT 翻页、缓慢大字和同一画面空等，不是成熟成片。

每镜头记录：用途、时长、来源（真实/生成）、参考文件、可变/不可变、模型/分辨率、预估积分、对应卖点、最终时间段。长片必须拆成当前工具支持的镜头时长，不假定单次能出 1–2 分钟。

稳妥的品牌一致性路径：**先生成/验收首帧 -> `first_frame` 生成短镜头 -> 验首中尾帧与动态 -> 允许的官网成片流程**。首尾帧和视频参考仅在实际模式支持时使用，不能把不支持的参数发给工具。

首帧提示词：
```text
为《[游戏名]》宣传片的[镜头用途]生成首帧。[比例/尺寸]。
严格沿用参考图的[人物身份/画风/结构]；主体正在[低复杂度动作前态]。
构图[景别/视角/重心]，统一光源和空间，主体完整。
后续运动是[轻推/呼吸/蒸气/风等]，保持适合动画的稳定几何。
无文字、Logo、UI、水印；不得新增角色或不存在的玩法。
```

视频提示词：
```text
[时长]秒，输入首帧是严格视觉基准，保持[脸/服装/建筑/车辆/道具]。
镜头只做[一个明确的小幅运动]，主体只做[一个允许动作]。
[背景]可轻微变化；[关键几何/数值/数量]保持不变。
不要切镜、变脸、肢体增生、物品变形、新文字、UI或水印。
完整沿用[二维/三维/像素等]画风，不变成另一种媒介。
```

首帧支持不了高复杂度动作时，换成稳定气氛镜头，别无限重生成。相机推近 2% 是某些静态画面的参考，不是所有游戏镜头的统一公式。

### 4. 音乐、音效、配音

#### BGM
用 `text_to_music`，不是音效工具。自定义模式必须有 `style`、`title`；`instrumental=true` 只在自定义模式生效。写清风格、乐器、节奏、情绪弧线、禁用元素；不要假设返回精确时长或天然无缝循环。

```json
{
  "customMode": true,
  "title": "[游戏名]品牌主题",
  "style": "与本游戏一致的器乐、节奏和空间感，适合宣传片，不模仿指定歌曲",
  "prompt": "先迅速建立动机，核心动作段保持脉冲，结果段抬升，结尾自然收束；无主唱、不遮掩动作音效",
  "instrumental": true,
  "negativeTags": "vocals, harsh clipping",
  "target_dir": "[已核验Maker项目绝对根]"
}
```

参考音乐/图片/视频按当前 schema 允许的公网 URL 或已记录生成资产引用。当前此工具没有本地上传步骤，不把未同步本地文件、data URL 硬塞进去；先检查合法时长/大小，不谎称已读取素材。简单模式最多5张图片，图片/视频/音频合计最多10项；音频6秒至30分钟且不超过500MB，图片不超过10MB，视频不超过241秒且不超过100MB。工具会尝试把已记录生成资产改写为远端引用，但不替你探测媒体时长。

#### 音效
独立效果用 `text_to_sound_effect`；一组用 `batch_sound_effects`。区分点击、碰撞、合成、奖励、升级、环境，写清材质、远近、力度、尾音和用途；每项 >0 且 ≤120秒，实际时长可能不同。返回文件保留原始格式，Maker 不自动保证 OGG。

#### 角色声音
1. 一个角色一个回合：`audition_voices_for_character`，年龄/性别、音色、速度、情绪、表演、录音质量写具体，试听台词**至少 100 个字符**，候选 1–3 个。
2. 展示全部候选声音，等待用户明确选择；推荐不等于同意。
3. `confirm_character_voice` 只在选择之后调用，消耗一个 Voice Slot，保存永久角色映射。
4. 再用 `text_to_dialogue` 提交角色名与台词；缺映射时回到试听，不伪造 voice ID，不并行确认同一项目。
5. 核对语言、停连、专有名词和情绪。Eleven v3 可用标签如 `[sad]`，仍以试听效果为准。

不同角色不并行跑试听/确认。当前映射复用只在身份和用途仍一致时成立，不把一次声音授权扩展给别的角色或项目。最终台词可指定语言和 `stability`（0～1，默认0.5）；语言代码按当前工具实际支持值填写，不凭名称猜代码。

试听台词应有真实表演跨度，而非重复凑字。提交前统计实际字符数；可用如下结构扩写到至少100字符：先打招呼和说明目标，再遇到一次小意外，最后重新鼓励玩家。语速、情绪和词汇都应属于这个角色，不能给沉默冷峻的角色套热情导游稿。

### 5. 声画验收

- 完整播放成片，另抽首、中、尾和镜头连接处检查；关键镜头不能只看封面。
- BGM 开始不硬撞、结尾不截断，按画面节奏淡入淡出；若官网不能混音，列出未完成项，不伪报处理。
- 实机音效对应真实动作，不把新生成的到账声叠在未到账画面；旁白清楚，不与音乐争抢。
- 检查爆音、静音段、缺音轨、音画漂移、跳帧、长黑帧、冻结、压缩损坏、错误水印与乱码。
- 720p 源片上采样成 1080p 不等于原生 1080p 生成。报告源规格与最终规格。
- 镜头已生成 ≠ 已接入；对照源文件哈希、最终镜头时间段与画面确认确实使用，不能拿生成收据替代成片证据。

## Maker 工具手册

以下基于本次可见 MCP schema（运行时包 0.0.38，2026-10-31）。工具名和字段以实际会话为准；更新提示不授权自动升级。没有暴露的工具不得靠猜 API 或直接付费供应商绕过。

### 1. 操作路由

| 需求 | 工具/动作 | 不可漏掉的约束 |
|---|---|---|
| 状态 | `maker://status` / `maker_status_lite` | 本地只读；不等于构建/已绑定/全部远端能力可用 |
| 单张新图 | `generate_image` | `name,prompt,target_size`；一般 `model=default` |
| 多张独立新图 | `batch_generate_images` | 两张以上，同一次请求保留逐项成功/失败 |
| 改已有图/扩展构图 | `edit_image` | `image,name,prompt,target_size`；不是新图工具替代品 |
| 视频 | `create_video_task` | 明确视频请求、费用门槛、模式与参考角色匹配 |
| 视频查询 | `query_video_task` | 有 task_id 才查；pending/running 后至少隔120秒 |
| 音乐/歌曲 | `text_to_music` | 非音效；自定义需 title/style，器乐项在自定义模式生效 |
| 单个/一组音效 | `text_to_sound_effect` / `batch_sound_effects` | 各项 ≤120秒，保留原格式 |
| 声音试听 | `audition_voices_for_character` | 描述具体，台词≥100字符，1–3候选，全部展示 |
| 声音确认 | `confirm_character_voice` | 本人明确选择后调用，占永久 Voice Slot |
| 最终台词 | `text_to_dialogue` | 已有确认映射；角色名与台词，不乱填 voice ID |
| 3D 生命周期 | `create_3d_asset` | start/query/get_options/continue/post_process；reviewed 需人工审核 |
| UrhoX 元数据 | `generate_resource_meta` | 确实供 UrhoX 使用时显式调用；不是其他引擎/宣发文件的前置步骤 |

构建、扫码、反馈和广告不是素材生成工具的隐含前提：不因物料需求自动调用 `maker_build_current_directory`、`generate_test_qrcode` 或 `get_ad_config`。如用户另要求扫码/构建等，按其实际规则处理。调研玩家反馈时优先只读 `get_debug_feedbacks(fetch_and_mark_processed=false)`，不为制作物料默认把反馈标为已处理。

### 2. 图片参数

- 普通新图/编辑默认 `model="default"`。仅用户明确指定后端时用 `nanobanana` / `gpt` / `image3`；不要把旧项目使用过 gpt 当成新项目指定。
- `aspect_ratio` 决定构图形状，`target_size="1920x1080"` 等是必填最终像素；`resolution` 是生成分辨率，不能拿来代替最终像素。
- `reference_images` 支持项目路径/适用 data URL 等，按工具具体 schema；每张本地或 data URL 参考 ≤10MiB。
- 新图最多14张参考；编辑为原图加最多13张额外参考。Image3 总输入最多3张（编辑原图计1张），不要把不同模型限额混用。
- 有 `reference_images` 时优先于旧 `reference_image`。多图注明各图职责，避免样式/身份互相污染。
- `quality` 依具体模型和后端，不承诺所有路由都支持同样等级；保留返回的实际模型信息。
- `transparent=true` 用于确实需要透明底的 Logo/切图；商店 Icon 与完整主视觉通常不能因此交透明底。透明输出要检查实际 alpha，不只看棋盘预览。

可执行参数模板（方括号需替换为已核验值，不原样提交）：
```json
{
  "target_dir": "[唯一Maker项目绝对根]",
  "name": "game_brand_hero_landscape",
  "model": "default",
  "prompt": "[用途、参考职责、主体、画风、构图、留白、允许/禁止变化]",
  "reference_images": ["assets/image/reference/character.png"],
  "aspect_ratio": "16:9",
  "target_size": "1920x1080",
  "resolution": "2K",
  "quality": "high"
}
```

### 3. 视频模式、输入与费用

模式：`text_to_video` / `first_frame` / `first_last_frame` / `multi_modal_reference`。图片角色为 `first_frame` / `last_frame` / `reference_image`，视频为 `reference_video`，音频为 `reference_audio`；不要混淆角色。某模型是否支持某模式、时长、分辨率，按当前 schema/返回说明核对。

当前工具规定的**估价**（不承诺实际账单）：

| model | 估价积分/秒 |
|---|---:|
| `2.0` | 200 |
| `2.5` | 300 |
| `wan` 480p | 42 |
| `wan` 720p | 84 |
| `wan` 1080p | 168 |

- `wan` 省略 resolution 时按1080p估价；省略 duration 或值为 -1 时按所选模型最大时长估价。`default` 的实际路由/计费不明时先核实，不能偷偷按最便宜模型估价。
- **单次估价超过1000积分**：先展示具体估价与“实际费用以生成时计费为准”，等待用户明确确认后才用同一请求 `user_confirmed=true`。≤1000 时不能预先填 true。不拆单规避本人确认门槛；同时披露完整计划总额。
- “普通积分许可自动同意”不能取代明确要求展示费用后的再次本人确认，也不能继承另一个游戏的预算。
- 参考图片 ≤30MiB，视频 ≤50MiB，音频 ≤15MiB；本地项目路径、公网 URL、data URL 的实际支持跟随模式/schema。`generate_audio` 用来声明是否生成伴随音频，不把静音源片当作自带BGM；`return_last_frame` 仅在确需后续衔接且模型支持时开启。
- 返回 pending/task_id 后先做其他工作，至少120秒后查；继续 pending/running，再隔至少120秒。不要每几秒轮询，不因本地请求超时重复 `create_video_task`。
- 原请求超时而 task_id 未知，先查官网任务历史/素材登记等可访问状态，报告执行状态不明；无证据不能认定没扣费。

5秒 wan 720p 的估价为 420 积分，两镜头估价840；这只是算例，不是所有宣传片的套餐价格。长片要分别估生成、可能重试和可选音频，没返回费用的项记“未知”，不要补成0。

### 4. 可选 3D，不把它强塞进纯2D宣发

只有用户的物料确实需要3D资产才进入。角色、生物、NPC、重要物品或明确美术方向采用 reviewed；普通低重要性物件可 direct。balanced 为一般默认，fast 只适合简单低重要性/一次性草稿，精细主体可 high_quality。

```json
{
  "action": "start",
  "target_dir": "[唯一Maker项目绝对根]",
  "payload": {
    "generation_strategy": "reviewed",
    "quality_tier": "balanced",
    "subject_type": "biped",
    "prompt": "[身份、比例、材质、用途与不可变特征]"
  }
}
```

- 文字 reviewed 提供 subject_type：biped（A-pose）、quadruped（中立站姿）、scenery、other。
- 记录 asset_id、task_id、step_id；query 查状态，get_options 查实际步骤选项。
- **所有返回审核预览展示给用户；本人明确批准之后才能 continue**，不自动填 confirm=true，不擅自开始最终模型生成。
- post_process 的 operation 为 rig / texture / retopology / convert。convert 明确格式；rig 先查可绑性。当前不支持 Tripo 动画重定向，不作可交付承诺。
- 使用 `local_delivery` 等返回路径；核对模型、贴图、材质、格式、比例和实际引擎导入需求。模型生成成功不等于已能在游戏里正确运行。

### 5. 本地投递、映射与故障分类

MCP 素材保留在经核验的 Maker 根目录：`assets/image`、`assets/video`、`assets/audio`、`assets/model`，映射以 `.maker/assets/generated-assets.json` 及实际返回为准。只输出不含凭证的路径/ID，不复制 `.maker-mcp/config.json`、登录文件或 Cookie 进交付包。

其他引擎需要引用时保留 Maker 原件，再在用户允许的目标范围复制/转换；不能挪走原件破坏后续编辑映射。纯宣发交付也不靠修改引擎文件“让生成生效”。

| 现象 | 先查 | 不要做 |
|---|---|---|
| 当前目录未绑定 | 目标根与账号/项目，是否存在已批准供应目录 | 自动 init/借另一个游戏扣费/构建 |
| 工具缺失 | 当前会话 tools、注册与具体版本 | 编造工具名、升级其他客户端 |
| 连接失败/超时 | 原始错误、阶段、工具/任务 ID | 立刻把所有失败归为 Maker 宕机 |
| 一批部分失败 | 逐项结果、成功文件与映射 | 整批重复生成导致重复扣费 |
| 生成成功但没文件 | 返回 workspace/local path、映射、实际落点 | 猜文件名、从别的项目拿同名图 |
| 看见图不等于可上传 | 实际尺寸/体积、文字、格式、最终字段 | 拿低清预览或无字母版当最终物料 |

音乐工具可能服务器端等待很久，超时返回task ID时保留ID查任务历史，不把音乐ID交给视频查询工具；没有对应查询能力则说明限制。声音试听是临时文件，永久配音、音效和音乐才按工具返回落到项目，不将试听当最终游戏资产。UrhoX元数据生成只使用官方工具，保留有效meta，不编造UUID，不借此自动构建。

只有明确诊断同一故障后做针对修复；覆盖已有资产、模型切换、付费回退、账号选择等本人停点依当前规则保留。问题报告上传诊断必须先获本次同意。

## 官网学习、操作、验收与交付

### 1. 在 Maker 官网学习这套 Skill

使用公开 GitHub 完整版 Markdown 链接；这比只给包入口更适合网页助手一次读取。不要声称 Maker 已把它永久装成 Skill，除非官网明确显示已保存且可跨会话调用。

可直接给官网助手：
```text
请阅读这份 TapTap 物料生成 Skill：https://raw.githubusercontent.com/xi-guanguan/urhox-distilled-docs/master/08-ai-workflow/xi-guanguan-TapTap%E5%85%A8%E5%93%81%E7%B1%BB%E7%89%A9%E6%96%99%E7%94%9F%E6%88%90Skill.md。
请实际打开全文；不能访问就告诉我，我会上传 Markdown，不要只根据标题猜内容。
把其中“创意生成只用 Maker MCP/官网、实机不能AI伪造、预算/声音/3D需本人确认、生成不等于发布”作为本项目制作约束。
我的游戏是：[名称/类型/横竖版/已实现卖点]，参考素材：[附件或项目素材]。
本次需要：[物料范围]，预算：[额度]，停在：[交付候选，不提审/发布]。
先结合当前发布字段给出缺项、工具/官网实际支持的步骤和预计费用，再按授权范围制作。
不要转第三方生成器，不用HTML、OpenFilm或程序化拼贴替代Maker生成。
```

若网页助手只能读一个链接，使用完整学习文档；不能抓 GitHub blob 时可使用同文件 Raw 链接。仍失败则下载 Markdown 后上传，或粘贴正文。读取失败不等于学会，当前对话读过也不等于长期记住。

### 2. 官网操作，不编造按钮与能力

1. 打开 `https://maker.taptap.cn`，观察当前页面，确认登录账号和目标项目；验证码、登录、付款、声音选择和3D审核由本人完成。
2. 找当前真实存在的图片/素材/视频/音乐/声音/3D入口，或让官网助手说明其可用能力。入口名不固定，不能凭本手册猜隐藏接口。
3. 上传参考前确认正确游戏、正确文件、输入职责和大小。参考图是输入，不把参考目录当作素材接收项目。
4. 填提示词、比例/尺寸/质量等当前页面有的选项；无该选项就说明缺口，不在页面外伪造功能。
5. 检查预估积分和本人批准停点后提交。生成后从当前任务/素材历史观察结果；超时先查状态，别重复点生成。
6. 对全部实际候选做对应预览。声音候选或3D审核图必须本人选，不能因为“推荐第一项”自动继续。
7. 下载正式文件而非缩略图，保存任务 ID、实际模型（若显示）、规格与已知计费；官网临时预览不等于永久资产。
8. 长片拼接、精确图层排版、字幕和混音只用当前官网**实际支持**的功能。没有则交镜头/模板包与缺口，不以“官网应该可以”代替完成。

MCP 与官网可以互为渠道，但切换前核对同一账号、项目与已发生任务；官网访问故障不会授权后台重复消费。浏览器操作若遇用户接管、inactive/unassigned等明确停点，等待用户恢复，不换浏览器或新空间绕过。

### 3. 非创意技术检查

本地检查不是替代生成。可使用现有图像工具和媒体探测工具读取宽高/字节/alpha、解码、查看音轨、生成接触表、计算哈希。不要为此擅自安装收费服务或改动项目代码。

图片检查：
- 实际像素与比例符合目标字段，文件可读，颜色/透明度正确，压缩后重查字与边缘。
- 中文逐字校对；Logo 在手机小图仍清楚；主体不被4:3/1:1/系统UI裁掉。
- 无错误手指/物体、背景变体、素材堆叠、假UI、乱码、水印、二维码或错误渠道文案。
- 截图对照真实底稿，包装比例达标，三张展示不同核心卖点，系列统一。

视频检查：
- 实际时长、宽高、比例、帧率、编码、体积符合字段；全片解码、播放通过。
- 检查首3–5秒、核心连续段、镜头连接、片尾；音轨存在不代表响度/同步正确。
- 真实/生成片段及剪辑性质能被追溯；核对画面占比、字幕/配音限制。
- 末尾自然淡出或完整收束，没有突然切断BGM；没有以黑帧补时长。

文案检查：游戏名、功能、版本、日期全对；简介与开发者的话不雷同；没有虚假承诺、受限联系方式/外链。

可选3D检查：实际可打开、贴图齐全、格式/比例合适，无法验证的引擎表现明确列待验证。

技术检查通过只证明文件与被检查项；不证明美术绝佳、真人体验好、平台审核必过或用户增长效果。

### 4. 最小交付包与账本

按真实范围组织，已有项目结构优先，不强制创建空目录：
```text
release-materials/
  final/                 唯一准备上传的候选
  source-maker/          保留生成原件或其明确索引；不挪走Maker原件
  reference-index/       参考来源/职责，不打包凭证
  copy.md                最终文案与字段映射
  manifest.json          最终文件、哈希、来源、状态、费用已知/未知
  review-notes.md        只在存在真实未决项时需要
```

一个清单项至少表达：
```json
{
  "asset_id": "hero_square_v2",
  "field": "square_promotion",
  "kind": "maker_generated_image",
  "generation_channel": "maker_mcp",
  "tool": "edit_image",
  "task_id": null,
  "source_asset": "横版母版的实际ID或路径",
  "model_actual": "未返回时填unknown，不猜",
  "size": [1440, 1440],
  "bytes": null,
  "sha256": null,
  "final_file": "final/实际文件名.png",
  "credits_estimated": null,
  "credits_reported": null,
  "spec_source_date": "YYYY-MM-DD",
  "validation": "pending",
  "upload": "not_requested"
```

这是待填结构，不把 null/pending 当完成。实机文件的 kind 改为 real_capture/engine_driven_demo 等，渠道改为真实采集来源；生成背景、真实截图、最终包装分别登记，不能把整张都归为 AI 实机生成。

交付报告写：本次生成/修改了什么、真实素材来自哪版游戏、所用 Maker 通道、实际文件位置、技术与视觉检查结果、费用已知/未知、未完成项，以及是否上传/提审/发布。没有做就写未执行，不用“都好了”合并多个状态。

### 5. 获准后才做后台回填

Maker 生成网站与 `developer.taptap.cn` 发布后台不同。生成任务不自动授权跨站修改发布草稿、签协议、提审或上线。

获准回填时：
1. 核对游戏/开发者/平台/阶段。读取后台现有包体、版本与发布方式，避免仍绑着几周前旧包，或误选带调试工具的验收包。
2. 每个字段使用清单中的最终候选，不用目录里同名早期版本。截图顺序和真实/包装类型逐项核对。
3. 保存后回读图片缩略图、尺寸/数量、顺序、视频字段、封面、简介、开发者的话、更新日志与主包版本；不能只信上传API返回成功。
4. 执行当前平台预检，区分阻断/警告；预检通过不等于最终审核通过。
5. 协议勾选、最终提交和正式发布按平台/工具要求保留本人批准；过去项目代同意过不代表此次已同意。
6. “预计发行日期”“预约页过审开放预约”“实际开放下载/试玩”“定时发布”是不同状态。写绝对日期、时区和当前状态；没有配置真正定时发布就不能承诺会到点上线。

用户要求把这套 Skill/文档上传 GitHub 时，先核对账号、仓库、分支、现有改动，只提交 Skill 文档与必要索引。不要上传原始聊天、私有美术、生成大视频、登录文件或源码；不要改变仓库可见性。完成后给可访问的文件链接，并核对远端确有该内容。

## 证据来源与适用边界

### 1. 本套 Skill 从什么经验提炼

来源为用户授权分析的另一段项目对话中 **2026-10-29～2026-10-30** 的 TapTap 物料制作、迭代与回填记录，以及该批物料的需求表、生成收据、镜头接入记录和交付说明。只公开方法，不上传原始聊天、账号凭证、私有素材或完整项目文件。

已在来源记录中观察到：
- 先核对官方物料要求与实际发布草稿，发现草稿可能还绑定旧包；制作与发布不是一回事。
- 两张参考约束的首帧通过 Maker MCP 生成，再生成两段各5秒的宣传镜头。返回的视频积分合计840；图片费用没有完整返回，不能据此声称全套仅840。
- 宣传图被指出是素材堆叠后，改成统一透视、人物关系、光线和叙事的完整主视觉；方版从横版重构，不简单裁切。
- 截图通过生成背景模板再结合真实游戏画面形成系列；需要检查最终上传的是包装版而非原始截图。
- 用户明确区分宣传片与约一分钟的玩法演示；玩法节奏不能只有反复点击生产器，需体现连续动作、结果、成长和其他真实特色。
- 宣传片 BGM 首尾收束、视频全片解码、原始生成镜头与成片接入关系都需要核验。
- 回填后还要核对图片顺序、文字、视频字段、普通玩家包、协议和预约/上线状态。

### 2. 哪些旧做法不直接继承

来源项目曾用 HTML/OpenFilm 程序化制作成片、采用本地技术合成，并用真实引擎驱动隔离前态做演示。这些是那个项目当时的实现与授权，**不是本套 Maker-only 工作流的默认生成方式**。

本套将创意生成限定到 Maker MCP/官网；官网没有相应合成能力时交素材包并说明缺口，而非偷偷走本地制片。真实实机作为必要的真实性输入单列，不能用 Maker 生成 UI 来冒充。

原游戏的美术、题材、镜头时长、自动积分许可、账号/项目、包体、预约日期和具体署名都不跨项目继承。文案中的短小红书口吻、不用emoji等可作为用户可选风格，不能压到所有游戏。

旧记录中的物料数字只是当时事实；本套另于2026-10-31读取官方小游戏专项与通用v4文档，明确区分2MB/500MB专项限制与通用字段更宽的限制，不沿用旧的统一模板。

### 3. 哪些是完整性扩展，而非宣称该项目全都验证过

为覆盖任意游戏，本套补齐 Icon/Logo、PC封面/壁纸、渠道海报、音乐/音效、声音试听确认、可选3D、异步查询、输入大小、费用门槛和官网路径。这些依据当前可见工具 schema 与官方要求编写；不声称它们已经在来源项目逐项运行成功。

官网具体按钮、长期“学习Skill”能力、精确图层锁定、长片混剪/混音等没有统一可保证入口，均要求实际观察后才采用。不能把可调用MCP工具等同于官网必有对应按钮。

推荐等级：**L2，参考学习与可执行流程**。来源核心制作路径有真实操作记录，扩展分支经参数/规则核对；本次制作的是 Skill，不额外消费积分跑完整素材回归，也没有证明所有游戏题材和官网界面都能一步完成。

### 4. 场景自测（不花积分的规则核对）

- 只做一个游戏 Icon：只读对应图片要求，不自动生成视频、3D或构建。
- 换成赛车/恐怖/像素游戏：替换视觉锚点、真实动作与受众，不携带客栈题材。
- 没有真实录屏但要求全由Maker生成“实机”：继续可生成项，明确不能用AI画面冒充，缺口不藏掉。
- 请求12秒 `2.0` 视频：估价2400，先展示账单估计与免责声明，等待明确确认，不能预填 true。
- 视频创建超时且已有任务ID：至少120秒后查状态，不重复创建。
- 三个试听已返回：全部展示，未选择不确认；3D审核同理。
- Maker未绑定：继续需求准备，不自动初始化、借项目、构建或迁移H5。
- 只要物料候选：交文件即停，不签协议/改发布草稿；获准回填后也不自动最终提审。
