# 账本、复现与验证

## 1. 不污染玩家档

每个场景有独立档案、日志与策略设置。导入玩家样本时只读复制，不覆盖源档，不接真实云保存。需要重置时只清当前测试命名空间，不清整个浏览器存储。持久化schema要版本化，历史日志不能按新算法强行回算成相同口径。

状态提交优先使用正常session的“先保存成功，再发布状态/演出”机制。加速模式不能绕过购买、领奖、入队等正常幂等保护。

## 2. 消费意图与崩溃恢复

对带资源成本的动作记录：意图ID、时间、订单/目标、报价、备选方案、预算占用、执行前快照摘要、最终结果和实际费用。

顺序：保存pending意图 → 真实动作提交并落档 → 回填确认/失败。意图日志写失败不发购买；主档失败不占最终花费；动作已成功但日志尾写失败，刷新后按耐久收据核对，不重复扣钱。无法确定的pending记待核对，不能当0花费。

日志尾部可以限量，但保留累计计数和截断数。最近2000条不是“完整历史”，不能用其中没有某类动作证明历史从未发生。导出要包含当前完整游戏状态、策略、种子/随机状态、时间口径、构建身份和账本，不只给截图或等级摘要。

## 3. 观测指标与卡点

分开记录：已尝试/成功/失败动作，资源获得/消费/余额，订单完成数，关卡/等级/建设进度，冷却/体力/棋盘/库存等待，模拟广告次数，保存错误，显式日切。

检测零进展、循环状态、资源收支异常、重复领奖、排队溢出、策略买错对象。等待本来可能是正常设计；给出状态和所缺依赖，不为了消除“等待”注入资源或跳任务。

复现时恢复同输入内容、初态、随机状态、策略及动作序列。只恢复seed而不恢复已消费随机次数，不能保证复现。业务时间可重复不代表网络宿主也可重复，真实外部调用需要单独证据。

## 4. 最小测试矩阵

| 主题 | 应检出的错误 |
|---|---|
| 时钟 | 负值/非法值/长间隔、后台追赶、切速跳时、跨日失败仍发布 |
| 调度 | 50×受错误硬上限变慢而不报告；CPU繁忙却先推进时间；保存失败后同帧继续操作 |
| 策略 | 漏一次性生产依赖、精确等级被合掉、重复购买、仓库存取循环 |
| 奖励与消费 | 日限额失效、同请求重发、报价变化、日志失败仍扣款、恢复后二次扣费 |
| 存档 | 导入覆盖原档、云同步污染、刷新丢设置、超长日志导出不可复现 |
| 证据 | 把人工前态当自然成长、把跨日算活跃游玩、把模拟SDK当真广告 |

可用故意改错步长/倍率/去重条件的隔离突变测试验证断言能抓错；不对共享工作树试验。每次恢复后逐字节核对，不能弱化断言来“全绿”。

## 5. 本项目依据与交付边界

核对日期2026-10-31，案例来源：`ReviewFastClock.ts`、`ReviewFastPlanner.ts`、`ReviewFastInventory.ts`、`ReviewFastEconomy.ts`、`ReviewFastPlay.ts`，以及对应时序/经济/日切测试和既有交付收据。

已观察到业务时钟不替换Date.now、可见性与CPU背压、显式+24h、正常规则规划、有限预算、pending消费恢复及带完整状态的导出。旧阶段“自动策略绝不花黄金”的结论不适用于后来带开关/预算的版本；始终按当前代码与导出设置判断。

来源包含本地WIP与历史包，不能因较新的本地文件就认定手机包也更新。本文新整理的是可复用流程，未在本次蒸馏中重新跑长线游戏或真实广告。交付中写清测试实际运行与仅建议的矩阵。推荐L2，不证明真人体验、自然成长速度或商业收益。
