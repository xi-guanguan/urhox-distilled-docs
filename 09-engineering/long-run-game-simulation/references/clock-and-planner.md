# 时钟、调度与规划器

## 1. 三种时间分离

- 业务时间：冷却、体力、订单、活动、商店报价等实际游戏规则读取，可注入。
- 现实墙钟：记录现实日期、真实宿主回调截止；不能随游戏50倍变化。
- 单调性能时钟：测每帧CPU耗时，避免系统时间校正影响工作预算。

固定业务时区与日界线，区分故事“第几日”和业务日。跨时区、夏令时、系统时钟回退、超长间隔、无效日期要按项目规则处理；“+24h”是明确时间操作，不永远等于任意时区的下一自然日。

业务时钟接口示意：
```ts
interface BusinessClock { now(): number }
interface SimulationMetrics {
  requestedMs: number;
  processedMs: number;
  droppedOrDeferredMs: number; // 名称与实际策略一致，不能假称一定会补跑
  realActiveMs: number;
  explicitJumpsMs: number;
}
```

## 2. 有背压的加速

调度伪流程：
1. 采样可见且运行中的现实间隔，限制异常长间隔。
2. 按目标倍速计算期望模拟增量，不立即发布全部未来时间。
3. 在CPU软预算内，逐步推进到下一个决策/事件边界：推进时钟 → 执行正常tick → 尝试一个合法动作。
4. 每次检查保存结果与暂停/接管。失败后同帧不再发动作。
5. 到预算就让帧；未处理时间按事先声明的策略丢弃/限额排队并记账，不能悄悄让时钟先走。后台/未就绪阶段不攒无限债。

本案例每模拟0.5秒决策，50倍目标约100决策/现实秒，使用8ms软预算；一次重工作可能超过软预算，然后应尽快让帧。这是案例参数，不是所有游戏的最佳常数。渲染、IO和自动策略复杂度都会让实际速度低于目标。

实测倍速用“实际推进的主动模拟时间/对应现实活跃时间”计算，说明分母是否包含准备等待；显式跨日跳跃另列。不能用设置按钮50×直接当报告里的实际50×。

## 3. 正常规则规划器

输入状态、内容定义、业务时间和策略选项；输出候选合法动作、等待原因与可选消费建议。执行仍经过真实session的校验与保存。

顺序可按游戏调整：完成已有订单 → 保留任务所需精确等级物品 → 合成有价值的库存 → 使用可用生产源 → 处理剧情/建设/奖励。不要为了“动作多”合掉必须保留的中阶物品，或删除有用库存。

必须识别：
- 当前订单的全部缺口与不同订单的权衡，而非永久只盯最低价单。
- 棋盘、仓库、奖励队列和已购买待入场物品，避免重复生产/购买。
- 自动生产器、限次产物、一次性点击产物、跨链生产依赖；不能假定所有来源是永久生成器。
- 满盘、无可合并项、生产冷却、体力不足、未解锁来源、需手动节点等不同等待原因。
- 精确等级任务保留、奖励合至合理等级再收取、已开启物件不能再合成等真实规则。

库存管理要避免“存进去→取出来→再存”的振荡：行动应减少已定义需求/压力，保留最近意图或冷却，检测重复状态并暂停。合法策略未必最快，报告策略约束，别为了漂亮进度秘密改概率。

## 4. 消费与模拟宿主

自动消费默认按用户明确选择的策略启用，读取真实报价；支持每日额度、保留余额、不同货币独立预算与关闭开关。比较直购、生产体力、泡泡等方案的成本和所省等待，但不要只凭“省了几秒”跨越许可预算。

报价过期、跨日、库存变化要重新校验；不可在执行时自动接受更高价格。模拟广告应由明确控制触发，使用正常日限额/奖励数额/请求去重，不能用无限QA领奖替代真实奖励逻辑；绝不调用真实广告SDK。

## 5. 可人工接管

先保证手动输入与保存安全，自动操作不能同一帧抢走拖拽物。控制条不盖住棋盘与关键按钮，窄屏和宽屏分别布局。开始/暂停/切速不额外推进未调度的间隙；切后台、资源未准备、场景切换时遵循声明的暂停策略。

跨日跳跃先准备并保存目标状态，再发布新业务时间；失败保持旧日期和报价。跳跃日志与主动游玩计时分开，不能把点一下“下一日”算作完整一天自动经营。
