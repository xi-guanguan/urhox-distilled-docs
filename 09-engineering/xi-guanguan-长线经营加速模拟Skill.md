## 长线经营加速模拟

目标不是“把游戏速度调快”，而是用可复现证据回答：玩家为何卡住、经济能否持续、长期定时/奖励是否正确。先复用真实规则与可用测试入口，不默认重写一套平行模拟器。

### 先分清四类工作

| 模式 | 用途与证据边界 |
|---|---|
| 正常规则自动游玩 | 输入合法动作，观察该策略下的成长；不代表所有真人行为 |
| 业务时钟加速 | 同一套时间规则下更快推进；不改变设备/宿主时间 |
| 显式离线/跨日跳跃 | 检查冷却、结算、日切；单独记录，不冒充主动游玩时长 |
| 前态注入/故障注入 | 直接测试后期与异常边界；不能证明到达该前态的自然流程 |

### 按任务读取

- 时钟、CPU背压、规划器、预算与手动接管：[时钟和真实规则](#reference-1)。
- 存档隔离、消费账本、导出、测试与证据：[日志和验证](#reference-2)。

### 执行

1. 确认要验证的成长目标、终止条件、允许资源/策略、随机性、时间规则与预算。保存输入版本和初始状态；不要只设置“无限运行”。
2. 将业务时间注入既有规则；墙钟只测现实耗时/真实宿主超时，性能时钟只做CPU预算。不要重写全局Date.now、系统日期或宿主超时。
3. 通过真实动作/reducer/session提交合法动作，观察真实成功/失败。规划器只决定下一步，不直接改金币、库存、订单或领奖标记。
4. 实施有背压的时间调度：只推进实际处理过的模拟时间，CPU不足降低实际倍速，不让定时器跑过尚未执行的决策；不积攒后台追赶债。
5. 对模拟状态、策略选项、随机状态和日志使用独立命名空间。玩家档只读复制，禁止写回或同步到真实云端。
6. 用阶段进度、资源收支、等待原因和完整可复现快照判断问题。保存失败、不可解释的状态、超预算或人工接管时暂停，不能吞错继续跑。

### 权限与停止条件

本任务不是免费资源生成器：特权前态、模拟奖励、消费策略要显式标记。真实广告/购买/云档/发帖等外部副作用不随自动游玩开启；模拟广告仅走隔离环境中的真实奖励规则和限额，并明确不是SDK验证。

用户要求“只观察”时不注入、不重置。游戏实现与GUI操作仍按当前项目授权执行；Maker画布等要求本人试玩的环境不能靠本Skill绕过。只请求模型测试时不擅自浏览器代玩。

设置现实耗时/模拟天数/动作数/等级等边界，遇保存失败、长时间零进展、同状态循环、预算问题自动暂停并导出原因，而非反复刷新或无限补资源。

### 交付

报告初态、策略、种子、输入/构建身份、目标倍速与实测倍速、主动模拟时长/跨日跳跃、资源账本、关键卡点和复现文件。明确哪些是正常规则、哪些是特权与模拟宿主。界面体验、真实广告、手机性能和真人耐心仍需对应证据。

## 时钟、调度与规划器

### 1. 三种时间分离

- 业务时间：冷却、体力、订单、活动、商店报价等实际游戏规则读取，可注入。
- 现实墙钟：记录现实日期、真实宿主回调截止；不能随游戏50倍变化。
- 单调性能时钟：测每帧CPU耗时，避免系统时间校正影响工作预算。

固定业务时区与日界线，区分故事“第几日”和业务日。跨时区、夏令时、系统时钟回退、超长间隔、无效日期要按项目规则处理；“+24h”是明确时间操作，不永远等于任意时区的下一自然日。

业务时钟接口示意：
```ts
interface BusinessClock { now(): number }
interface SimulationMetrics {
  requestedMs: number;
  processedMs: number;
  droppedOrDeferredMs: number; // 名称与实际策略一致，不能假称一定会补跑
  realActiveMs: number;
  explicitJumpsMs: number;
}
```

### 2. 有背压的加速

调度伪流程：
1. 采样可见且运行中的现实间隔，限制异常长间隔。
2. 按目标倍速计算期望模拟增量，不立即发布全部未来时间。
3. 在CPU软预算内，逐步推进到下一个决策/事件边界：推进时钟 → 执行正常tick → 尝试一个合法动作。
4. 每次检查保存结果与暂停/接管。失败后同帧不再发动作。
5. 到预算就让帧；未处理时间按事先声明的策略丢弃/限额排队并记账，不能悄悄让时钟先走。后台/未就绪阶段不攒无限债。

本案例每模拟0.5秒决策，50倍目标约100决策/现实秒，使用8ms软预算；一次重工作可能超过软预算，然后应尽快让帧。这是案例参数，不是所有游戏的最佳常数。渲染、IO和自动策略复杂度都会让实际速度低于目标。

实测倍速用“实际推进的主动模拟时间/对应现实活跃时间”计算，说明分母是否包含准备等待；显式跨日跳跃另列。不能用设置按钮50×直接当报告里的实际50×。

### 3. 正常规则规划器

输入状态、内容定义、业务时间和策略选项；输出候选合法动作、等待原因与可选消费建议。执行仍经过真实session的校验与保存。

顺序可按游戏调整：完成已有订单 → 保留任务所需精确等级物品 → 合成有价值的库存 → 使用可用生产源 → 处理剧情/建设/奖励。不要为了“动作多”合掉必须保留的中阶物品，或删除有用库存。

必须识别：
- 当前订单的全部缺口与不同订单的权衡，而非永久只盯最低价单。
- 棋盘、仓库、奖励队列和已购买待入场物品，避免重复生产/购买。
- 自动生产器、限次产物、一次性点击产物、跨链生产依赖；不能假定所有来源是永久生成器。
- 满盘、无可合并项、生产冷却、体力不足、未解锁来源、需手动节点等不同等待原因。
- 精确等级任务保留、奖励合至合理等级再收取、已开启物件不能再合成等真实规则。

库存管理要避免“存进去→取出来→再存”的振荡：行动应减少已定义需求/压力，保留最近意图或冷却，检测重复状态并暂停。合法策略未必最快，报告策略约束，别为了漂亮进度秘密改概率。

### 4. 消费与模拟宿主

自动消费默认按用户明确选择的策略启用，读取真实报价；支持每日额度、保留余额、不同货币独立预算与关闭开关。比较直购、生产体力、泡泡等方案的成本和所省等待，但不要只凭“省了几秒”跨越许可预算。

报价过期、跨日、库存变化要重新校验；不可在执行时自动接受更高价格。模拟广告应由明确控制触发，使用正常日限额/奖励数额/请求去重，不能用无限QA领奖替代真实奖励逻辑；绝不调用真实广告SDK。

### 5. 可人工接管

先保证手动输入与保存安全，自动操作不能同一帧抢走拖拽物。控制条不盖住棋盘与关键按钮，窄屏和宽屏分别布局。开始/暂停/切速不额外推进未调度的间隙；切后台、资源未准备、场景切换时遵循声明的暂停策略。

跨日跳跃先准备并保存目标状态，再发布新业务时间；失败保持旧日期和报价。跳跃日志与主动游玩计时分开，不能把点一下“下一日”算作完整一天自动经营。

## 账本、复现与验证

### 1. 不污染玩家档

每个场景有独立档案、日志与策略设置。导入玩家样本时只读复制，不覆盖源档，不接真实云保存。需要重置时只清当前测试命名空间，不清整个浏览器存储。持久化schema要版本化，历史日志不能按新算法强行回算成相同口径。

状态提交优先使用正常session的“先保存成功，再发布状态/演出”机制。加速模式不能绕过购买、领奖、入队等正常幂等保护。

### 2. 消费意图与崩溃恢复

对带资源成本的动作记录：意图ID、时间、订单/目标、报价、备选方案、预算占用、执行前快照摘要、最终结果和实际费用。

顺序：保存pending意图 → 真实动作提交并落档 → 回填确认/失败。意图日志写失败不发购买；主档失败不占最终花费；动作已成功但日志尾写失败，刷新后按耐久收据核对，不重复扣钱。无法确定的pending记待核对，不能当0花费。

日志尾部可以限量，但保留累计计数和截断数。最近2000条不是“完整历史”，不能用其中没有某类动作证明历史从未发生。导出要包含当前完整游戏状态、策略、种子/随机状态、时间口径、构建身份和账本，不只给截图或等级摘要。

### 3. 观测指标与卡点

分开记录：已尝试/成功/失败动作，资源获得/消费/余额，订单完成数，关卡/等级/建设进度，冷却/体力/棋盘/库存等待，模拟广告次数，保存错误，显式日切。

检测零进展、循环状态、资源收支异常、重复领奖、排队溢出、策略买错对象。等待本来可能是正常设计；给出状态和所缺依赖，不为了消除“等待”注入资源或跳任务。

复现时恢复同输入内容、初态、随机状态、策略及动作序列。只恢复seed而不恢复已消费随机次数，不能保证复现。业务时间可重复不代表网络宿主也可重复，真实外部调用需要单独证据。

### 4. 最小测试矩阵

| 主题 | 应检出的错误 |
|---|---|
| 时钟 | 负值/非法值/长间隔、后台追赶、切速跳时、跨日失败仍发布 |
| 调度 | 50×受错误硬上限变慢而不报告；CPU繁忙却先推进时间；保存失败后同帧继续操作 |
| 策略 | 漏一次性生产依赖、精确等级被合掉、重复购买、仓库存取循环 |
| 奖励与消费 | 日限额失效、同请求重发、报价变化、日志失败仍扣款、恢复后二次扣费 |
| 存档 | 导入覆盖原档、云同步污染、刷新丢设置、超长日志导出不可复现 |
| 证据 | 把人工前态当自然成长、把跨日算活跃游玩、把模拟SDK当真广告 |

可用故意改错步长/倍率/去重条件的隔离突变测试验证断言能抓错；不对共享工作树试验。每次恢复后逐字节核对，不能弱化断言来“全绿”。

### 5. 本项目依据与交付边界

核对日期2026-10-31，案例来源：`ReviewFastClock.ts`、`ReviewFastPlanner.ts`、`ReviewFastInventory.ts`、`ReviewFastEconomy.ts`、`ReviewFastPlay.ts`，以及对应时序/经济/日切测试和既有交付收据。

已观察到业务时钟不替换Date.now、可见性与CPU背压、显式+24h、正常规则规划、有限预算、pending消费恢复及带完整状态的导出。旧阶段“自动策略绝不花黄金”的结论不适用于后来带开关/预算的版本；始终按当前代码与导出设置判断。

来源包含本地WIP与历史包，不能因较新的本地文件就认定手机包也更新。本文新整理的是可复用流程，未在本次蒸馏中重新跑长线游戏或真实广告。交付中写清测试实际运行与仅建议的矩阵。推荐L2，不证明真人体验、自然成长速度或商业收益。
